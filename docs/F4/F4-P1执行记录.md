## 二、三个探查结论（任务书要的三条自述）

### 1. `round_id` 的来源 —— **本轮之前没有，现在服务端生成**（口径 F65）

查过 `/explain` 响应的每一个字段。**没有任何稳定的轮标识**，而两个看起来像的都不能用：

| 候选 | 为什么不行 |
| --- | --- |
| `retrieval.signature` | 它只认**提问 + 命中切片**（`ContextPack.signature()` 的定义）。同一个人把同一个问题问两遍会得到**同一个值** —— 拿它当幂等键，第二轮的标记会被幂等成第一轮的，而表现是「点了没反应」 |
| `session_id` | 它是整场会话（一次页面加载），不是一轮 |
| `request_signature` | 有，但 `RoundResult` 里的它没有进响应；且它含 system 与 messages，注入一旦发生它就变了 —— 一个会被自己改变的标识 |

处置：`/explain` 里 `str(uuid.uuid4())`，随响应返回 `round_id`，前端原样带回来。
**一次 `/explain` = 一轮**；轮内由审查驱动的重生成不新开一个（它们在同一次
`run_round` 里，本来就共用这一个 id），与 PRD §13.0「轮 = 用户可见的一次输出」一致。

### 2. `slice_ids` 有没有落库 —— **有，但「非空」没有护栏**

`retrieval_executed.payload.slice_ids` 从阶段 6 就在，而且每项带 `document_id`
（`events.py` 的 `_slice_identities`）。所以任务书说的「没有 → 补上」不适用。

**但发现了一个真的洞**：`f1_event_payload_ok` 判的是「键在不在」，
而**空数组 `[]` 完全通过它**（不是 SQL NULL、不是 JSON null、不是空字符串）。
于是「检索命中了 5 片，而事件里的 slice_ids 是空的」**没有任何东西会红** ——
而那正是护栏指标「重复提问率」的唯一数据来源（口径 F62），漏了补不回来。

补了两层，形态与 `20260913090000` 那条 `deck_id` 不变量相同：
- 数据库：`f4_event_slice_ids_ok` + `style_events_slice_ids_ok` CHECK；
- Python：`events._slice_ids_problem`，构造时就抛。

⚠️ **空检索是例外，放行**（`slice_count = 0`）。一片都没检索到是合法状态，
而且它**更该**被采集到（PRD §6.2：空检索是显式失败，比答非所问安全）。
一并拒掉就是口径 F50 那条教训的复发。

⚠️ 这条能做成 DB CHECK、而上传那两个字段只能留在 Python 侧，差别在于：
这四个讲解事件由服务端发，`/explain` 把 `record_events()` 的结果原样放进响应的
`events` 字段 —— **被 23514 拒掉的事件在这里不是静默消失的**。

### 3. 一处**偏离任务书**的地方：`slice_ids` 是 `text[]` 不是 `uuid[]`（口径 F66）

任务书与 F4 方案 §3.1 都写 `uuid[]`。**切片的身份本来就不是一个 uuid**：
`slices` 的主键是 `(document_id uuid, slice_id text)`，后者是文档内局部 id，
而 2026-09-12 的真库观测记着「一门课的两份讲义都有 `s001`」。

`uuid[]` 只有两条出路，都是坏的：

| 写法 | 后果 |
| --- | --- |
| 存 `document_id` | 粒度退化成**整份讲义**：标记一页 → 这份讲义以后每次命中都注入。**恒触发**，而恒触发的限定语最难发现（输出看起来完全正常，只是每轮多讲一句） |
| 只存 `slice_id` | 它不是 uuid，写不进 `uuid[]`；硬转 text 又会让 A 讲义的 `s001` 与 B 讲义的 `s001` 撞成同一个身份 —— **误触发，且不可见** |

处置：`text[]`，元素是 `'<document_id>:<slice_id>'`，唯一拼法出处
`api/api/marks.py` 的 `slice_key()`（两段里出现分隔符就抛）。
`&&` 与 GIN 在 `text[]` 上一样用。已登记为口径 F66。

### ⚠️ 守卫 2 / 3 的两端从哪来 —— **单测层这条是空的，真库层才成立**

被问到「两端各自从哪来」，查完的答案是：**单测层两端同源**。
`tests/test_marks.py` 里写入侧是 `/explain` 响应的 `slice_keys`、读取侧是下一轮的
`slice_keys_of(ctx)`，**两个都出自 `api/api/marks.py` 的 `slice_key()`**。
同源意味着分隔符一改两端一起改，交集照样非空，断言照绿 ——
所以「写入侧与读取侧拼出的是同一份」这件事在那一层**是构造保证的，无从证伪**。

而它一旦不成立，表现正是最难发现的那种：**接口 200、表里有行、什么都不注入**。

分两层处置，各写各的（口径 F34）：

| 层 | 能钉住什么 | 在哪 |
| --- | --- | --- |
| 单测 | ① **格式**：落进表里的那一段 == 「两段用冒号连起来」，右边**手写，刻意不调 `slice_key()`** —— 改 `KEY_SEPARATOR` 就红（已演示：改成 `/` → 2 条红）。② **敏感性**：写入侧被改坏一个字符 → 下一轮必须不注入，且把「200 / 有行 / 不注入」三个症状一起断言 | `TestBothEndsOfTheKey` |

### 顺带找出并修掉的一处（写这一节的 SQL 时发现的）

`f4_event_slice_ids_ok` 里那个空检索例外，第一版写的是
`coalesce((payload ->> 'slice_count')::int, -1) = 0`。两个问题：

- **`slice_count` 不是数字时抛 22P02**。一条 CHECK 应当判假，而不是让 insert
  以「数据库坏了」的错误码失败；`add constraint` 校验存量时它甚至会让整条迁移以
  22P02 而不是 23514 失败，而那两个码指向完全不同的排查路径。
- 那个 cast 会把 JSON 字符串 `"0"` 也算成 0，而 Python 侧那份镜像
  （`payload.get("slice_count") == 0`）不认字符串 —— **两份镜像给不同答案**。

改成 `payload -> 'slice_count' is not distinct from '0'::jsonb`。
用 `is not distinct from` 而不是 `=` 又是一条：键缺失时 `NULL = '0'` 求值为 **NULL**，
函数返回 NULL，而**结果为 NULL 的 CHECK 是通过的** —— 那一行会悄悄写进去。
R18 里补了这两条边界断言（缺 `slice_count` / 字符串 `"0"` 各一条），
`test_python_and_sql_agree_on_the_non_empty_rule` 的样本也各加了一条。

## 六、交付后的操作顺序 —— **迁移必须先于部署**

反了的话有两种失败叠在一起，而且方向相反：

- `confusion_marks` 表还不存在 → `POST /marks` 报 **502**（响亮，看得见）；
- `f1_event_required_keys` 还不认识 `confusion_mark_created` → 那条事件被 **23514**
  全部拒掉，而接口**照常返回 200**（埋点失败不打断主链路，口径 F42）——**静默**；
- `/explain` 那一侧：查 marks 会 404，被 `_confusion_for_round` 接住，
  讲解**照常返回 200**，注入永远不触发，错误在响应的 `confusion.error` 里。

所以：

### ① **先记数**（跑迁移之前，两句 SQL）

不先记的话，迁移成功之后「存量里没有坏行」与「本来就一行都没有」**分不开** ——
同 cascade 那条「删之前先记数」。两句都在 Supabase SQL Editor 里跑。

**a. 讲解轮事件的总条数**（按类型分列，不合成一个数：`retrieval_executed`
是带 `slice_ids` 的那个、也是本轮 CHECK 管的那个；`explain_turn` 是「一轮」
本身的计数。两个数不等就说明有轮次的检索事件没落上，那是另一件事）：

```sql
select event_type, count(*) as 条数,
       min(created_at) as 最早, max(created_at) as 最近
from public.style_events
where event_type in ('retrieval_executed', 'explain_turn')
group by event_type
order by event_type;
```

**b. 其中 `slice_ids` 缺失或为空数组的条数**（末列才是决定迁移会不会回滚的那个）：

```sql
select
  count(*)                                                             as 检索事件总数,
  count(*) filter (where payload -> 'slice_ids' is null
                      or jsonb_typeof(payload -> 'slice_ids') = 'null') as 缺失,
  count(*) filter (where jsonb_typeof(payload -> 'slice_ids') = 'array'
                     and jsonb_array_length(payload -> 'slice_ids') = 0) as 空数组,
  count(*) filter (where jsonb_typeof(payload -> 'slice_ids') = 'array'
                     and jsonb_array_length(payload -> 'slice_ids') = 0
                     and payload -> 'slice_count'
                         is distinct from '0'::jsonb)                    as 迁移会拒掉
from public.style_events
where event_type = 'retrieval_executed';
```

三列的含义**不一样，别合并着读**：

| 列 | 含义 | 迁移会怎样 |
| --- | --- | --- |
| 缺失 | 键压根不在 / 是 JSON null | 已经被 `f1_event_payload_ok` 挡着，**理论上应为 0**；不为 0 说明那条更老的 CHECK 有洞 |
| 空数组 | `[]` | 通过了旧护栏 —— 本轮补的正是它 |
| **迁移会拒掉** | `[]` 且**不是**空检索 | **> 0 就会 23514 回滚** |
