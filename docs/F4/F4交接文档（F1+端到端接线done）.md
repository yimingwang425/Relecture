### 人工验收里真正发现的那条红：React #418

现象：`/onboarding/style` 的 Console 报 hydration 文本不匹配，**报与不报各半**。

根因：`useState(() => makeFlips(TOTAL_STEPS))` 写在客户端组件里，
SSR 跑一次、hydrate 又跑一次，两次 `Math.random()` 约一半概率不同。

修法：随机上移到服务端页面抽一次，作为 prop 传下去。

**为什么判红而不是警告**：服务端 HTML 先绘制、hydrate 后被换掉，用户看到/点到的是哪一版不确定；
阶段 4 记的 `left_variant` 可能记的是客户端那次，而用户是对着服务端那版做的选择——
位置随机化的目的（让点击可归因）会失效。

**护栏第一版是空转的，被它自己的反向控制抓出来**：
初版只查字面的 `Math.random(`，而真实 bug 是 `makeFlips(...)`——随机藏在一层调用后面，
客户端源码里根本没有那几个字。改成按函数体推导名单后才真的会红。

### CC 主动补的两处

- **对照臂也发 `style_onboarding_completed`**：任务书字面只要求主臂满足，
  但完成率按臂分组，text 臂不发那条曲线就只有一半，**且不会以任何形式报错**。
  代价是 `steps_completed` 两臂含义不同（主臂 1–6、对照臂恒 1），三处写明不可跨臂比较。
- **`documents.owner` 必须等于所引用课程的 owner**（接线阶段 4）：
  RLS 的 `with check` 只问「这一行的 owner 是不是我」，不问「我引用的那门课是不是我的」。
  不补的话 B 能把文档挂进 A 的课，A 一检索就召回 B 的内容。**这条不在任何一版探查清单上**。

### 人工验收发现的红：`style_pair_shown` 丢 step 1

`style_pair_chosen` = 6，`style_pair_shown` = **5**，缺的固定是 **step 1**，概率性发生。

根因（推断，未坐实但不影响处置）：step 1 的事件是这次页面加载中浏览器对 Supabase 的第一个请求，
可能复用了服务端已关闭的 keep-alive 连接；**浏览器会自动重发幂等 GET，但不会自动重发 POST**。

**判红的理由不是「网络会抖」**——网络抖是必然的。红的是**失败之后没有任何补偿**。

处置：`createEventQueue` 退避重试 + 落 sessionStorage 跨页面存活 + 瞬时/永久分类走白名单。
**没有选「首屏事件延后到 client 就绪」**——那只降低概率、让 bug 更难被抓到，
是拿判据的分辨力换一个好看的数字。

## 三、端到端接线（探查出来的，PRD 里没有这一项）

### 3.1 探查结论：链路不存在，不是断了一处

F1 做完后做的一次只读追踪，发现**两条各自完整、互不相接的半截链路**：

```
TS 半截（终点是屏幕）：
  style_config → loadStyleRow() → configOf() → 渲染成档位标签 → 终点

Python 半截（起点不是数据库）：
  scan/points.py 写死的配置点 → StyleConfig → render_style_rules()
  → build_system() → run_round() → model.complete()
```

四处断点，每一处单独就足以断开：没有任何 Python 读 Supabase；
没有服务把 `explain` 暴露出来；web 没有生成入口；
`run_round` 的调用方**只有单测与扫描实验**。

**最刺人的一句**：A5 想比较的那个东西（哪种采集方式产出更好的配置）当时没有下游可比。
F1 五个阶段验的全是「配置存得对不对、采得对不对」。

### 3.4 几条重要的技术决策

- **v1 不建 hnsw ANN 索引**：检索选型证据全部来自精确余弦扫描，
  建 hnsw 是观测范围与应用范围错配（F23 形态）；单课数十切片精确扫描无压力。
  **为不存在的性能问题引入真实的召回损失不划算。** 触发条件已写具体数字。
- **`course_id` 只放 `documents`，`match_slices` 走 join**：
  冗余到 slices 的唯一强理由是让 ANN 按课裁剪，不建 ANN 之后那个理由消失了。
- **唯一索引改 `(owner, course_id, sha)`**：
  `(owner, sha)` 会拦掉真实场景（同一份讲义跨学期复用），
  而「被数据库拦住且说不清为什么」比多花一次 embedding 伤得多。
- **`documents` 加 5 个版本列**（含 `split_threshold_chars`）：
  后者是**改变切片结果的输入**，当前 0 触发所以今天看不出问题，
  一旦按 embedding 窗口注入值，新旧切片就再也分不开。
- **OpenAI ZDR 不申请**：ZDR 面向企业级/高合规场景，个人开发者申请通常不受理，
  列为待办等于挂一个永远不会完成的项；API 默认不用于训练，30 天保留仅用于滥用监测。
  触发条件：数据类型改变或面向机构客户时重评。
- **部署平台 Railway → Render**：理由是**账号级的不是技术的**（Railway 免费层被另一项目占用）。
  Dockerfile 里原四条技术理由对 Render 逐条同样成立，原样保留。
  PRD §13.3 服务商改 Render，**部署地仍是新加坡**。

## 五、人工验收的方法论（四轮攒出来的）

### 清单顺序 ≠ 执行顺序

每一轮都出现过「按编号走会撞墙」的情况：

- **迁移必须先于部署**。反了的话事件全被 23514 拒，而功能照常返回 200——静默失败
- **不可逆步骤要标出来**：走完 6 步会写 `onboarded_at`，之后进不去 onboarding 页，
  所以「连开 10 次看随机」「看第 2 步分叉」必须在走完之前做，且要用**另一个账号**
- **臂在注册时定死**，选不了，只能建到为止；要先查 `f1_arm` 再决定哪个账号走哪条臂
- **cascade 验证必须最后做**，且**删之前要先记数**——不先记的话，
  删完看到「0 条」分不清是 cascade 生效还是本来就没有
- **env 相关的测试有顺序**：503（未配 key）要在配 key 之前做，否则要再部署两次

### 判据要在跑之前定死

「多开几次看随机」不是判据。实际用的是：**连开 10 次，两个取值都至少出现 1 次，
全同判红**（公平硬币下全同概率 2⁻⁹ ≈ 0.2%）。
不定死的话，开到第 6 次全一样会自然而然想「再开两次看看」。

### 几个典型的坑（我自己踩的）

- **查错了列**：`deck_id` 是列不在 payload，`payload->>'deck_id'` 必为 null
- **编了字段名**：`reason` 不是任何事件的字段，实际叫 `failure_kind`
- **拿到坏结果**：Supabase SQL Editor 某次 `limit 10` 返回 20 行、`created_at` 重复，
  据此判了两条红，用 `count(*)` 重查是 `3/3` 全部正常
- **区间重叠**：P0 是 30–120、P3 是 15–40，在 30–40 上重叠，
  所以「各自达标」在一个两次返回同一段 35 字文字的实现上也全绿。
  补法是加 `mean(P0) > mean(P3)`，只比大小不引入新阈值
