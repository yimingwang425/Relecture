## 〇、先读：本轮与任务书的一处偏离（影响第 4 项怎么读）

任务书 §4 写「本轮只做前端发送 `confusion_mark_created`，走 `createEventQueue`」。
**实际没有这样做**，理由是 P1 已经交付的代码：

- `POST /marks` 在**服务端同一次请求里**就发这条事件（`api/api/main.py` 的
  `_record_mark_event` → `events.build_mark_event`），三个必需字段齐全，另带
  `created` 与 `course_id` 列，带重试；P1 守卫 7「埋点写库」钉的就是它。
- 前端再经队列发一条 = **每次点击两行**，第 4 项「多了一行」会读成 2。

所以前端的责任变成：**请求体里带上 `session_id` 与 `course_id`**
（服务端缺 `session_id` 会**跳过**这条事件，不现编），且**自己不另发**。
`verify:logic` 十四节断的就是这两件事（含反向控制）。

## 二、执行顺序依赖

```
第 1 轮讲解（拿到 round_id）──► 第 1 项 点按钮 ──► 第 4 项 查事件
                                   │
                                   ├──► 第 2 项 第 2 轮：同一问题再问（注入只在「标记之后的轮」可见）
                                   └──► 第 3 项 第 3 轮：完全不同的问题
第 5 项 观察项：任意时刻
```

- **没有 `round_id` 就没有按钮**：必须先完成一轮讲解（按钮在那一轮回答下面）。
- **注入效果在第二轮才看得到**：第 1 轮自己的 `confusion.injected` 反映的是「此前」的标记，与本次点击无关。
- 第 2、3 项必须在第 1 项**成功之后**做，否则两者都是 `false`，第 3 项会假绿。

## ⚠️ 不可逆步骤

**第 1 项点下去的那一行删不掉**：`confusion_marks` 只授 select / insert，没有 delete（口径 F60）。
这是那条口径的直接代价；该账号内测前整个删除，marks 随 cascade 走。
**因此第 1 项只点一个 `round_id`**，不要为了「再看一眼」在别的轮次上多点。

## 三、验收项

### 第 1 项 · 按钮状态与幂等

**操作**

1. 问：`这门课讲的能源问题主要有哪些？`，等到回答出现。
2. 在 Network 里点开这次 `explain` 的响应，抄下 `round_id = ___`、`slice_keys = ___`。
3. 点这一轮下面的「这部分没看懂」。
4. 在 Network 里对这次 `marks` 请求右键 → **Copy → Copy as fetch**，先存在记事本里。
5. 刷新页面。
6. 打开 Console，粘贴第 4 步复制的 fetch 并执行（**这就是「同一 `round_id` 再提交一次」**，见下方注记）。

**判据（跑前定死）**

| 观测 | 绿 | 红 |
| --- | --- | --- |
| 第 3 步后按钮文案 / 状态 | 「已记下」且灰掉不可点（DOM：`data-mark-state="marked"`） | 仍可点 / 文案没变 / 出现红字 |
| 第 3 步 `marks` 请求体 | 恰好 5 个键：`round_id` `slice_ids` `question` `session_id` `course_id`；`round_id`、`slice_ids` 与第 2 步抄的**逐字相同** | 多键 / 少键 / 值不同 |
| 第 3 步 `marks` 响应 | `200`，`created: true`，`events.emitted: 1` | 非 200；或 `events.emitted` ≠ 1（读 `events.skipped_reason` / `error`） |
| 第 5 步刷新后 | 页面回到空会话；新问一轮后，新一轮的按钮是可点的「这部分没看懂」 | 新一轮的按钮一出现就是「已记下」 |
| 第 6 步响应 | `200`，`created: false` | 409 / 422 / 5xx |
| SQL ① 行数 | **1** | ≠ 1 |

```sql
-- ① 同一 round_id 在表里几行
select count(*) from public.confusion_marks where round_id = '<第 2 步的 round_id>';
```

> **注记（如实登记）**：讲解页的轮次只活在内存里，刷新后**那一轮本身就不在页面上了**，
> 所以「刷新后在同一轮上再点一次」在 UI 上走不到。第 6 步用 Copy as fetch 重放，
> 发出去的是**同一个请求体**，与「刷新后再点」对服务端是同一件事。
> 若要额外确认前端不为 `created: false` 分支，那条是 `verify:logic` 14.6 断的，不在本清单里。

### 第 2 项 · 标记过的切片再被命中 → 注入

**操作**：（第 1 项之后）同一门课、**逐字相同**的问题再问一次。

**判据**

先查**前提**：本轮响应的 `slice_keys` 与第 1 项第 2 步抄的那一份**至少有一个相同**。
前提不成立 → 这一项**记「未观测」，不记红也不记绿**（检索没命中同一批，注入本就不该发生）；换一个第 1 轮就命中过的问题再试一次。

| 观测（本轮 `explain` 响应） | 绿 | 红 |
| --- | --- | --- |
| `confusion.injected` | `true` | `false` |
| `confusion.note` | 与 `api/api/marks.py` 的 `CONFUSION_NOTE` **逐字相同**（F58：「用户此前看过这部分内容并标记为没看懂。换一个切入点重讲，不要照搬上次的表述。」） | `null` / 措辞不同 |
| `confusion.matched_slice_keys` | 非空，且是本轮 `slice_keys` 的子集 | 空 / 含本轮没有的键 |
| 页面 | 这一轮 meta 行出现「你之前标过这几页没看懂，这次换了个切入点讲」 | 不出现 |

### 第 3 项 · 不相干的切片 → **不**注入（防恒触发，不能漏）

**操作**：（第 1 项之后）问一个与第 1 轮**完全不同主题**的问题（跑前在这里写下来：`________________`）。

**判据**

先查**前提**：本轮 `slice_keys` 与第 1 项抄的那一份**交集为空**。
前提不成立 → **记「未观测」**，换一个问题重来，直到交集为空（这一项的全部分辨力都在这个前提上）。

| 观测 | 绿 | 红 |
| --- | --- | --- |
| `confusion.injected` | `false` | **`true` —— 恒触发，最难发现的那种（输出看起来完全正常）** |
| `confusion.note` | `null` | 非空 |
| `confusion.matched_slice_keys` | `[]` | 非空 |
| `confusion.marked_rounds` | `0` | > 0 |

### 第 4 项 · 事件表多了**一**行，三个字段齐全

**判据**（第 1 项第 3 步之后、**第 6 步重放之前**查一次；重放之后再查一次）

```sql
select e.created_at, e.session_id, e.course_id,
       e.payload -> 'round_id'         as round_id,
       e.payload -> 'slice_ids'        as slice_ids,
       e.payload -> 'mark_count_after' as mark_count_after,
       e.payload -> 'created'          as created
from public.style_events e
where e.event_type = 'confusion_mark_created'
  and e.payload ->> 'round_id' = '<第 1 项的 round_id>'
order by e.created_at;
```

| 时点 | 绿 | 红 |
| --- | --- | --- |
| 重放之前 | **恰好 1 行**；`round_id` / `slice_ids` 与第 1 项抄的相同；`mark_count_after` = `marks_before + 1`；`session_id` 非空；`course_id` = `192ce225-acc7-4fc9-a200-79e57a0b0ae9` | 0 行（事件没落：看第 1 项响应的 `events`）/ **2 行（前端另发了一条）** / 任一字段缺 |
| 重放之后 | 2 行，第二行 `created = false`，`mark_count_after` **不涨**（与第一行相同） | 仍是 1 行 / 第二行 `mark_count_after` 涨了 |

> 重复提交**也发事件**是 P1 的设计（`build_mark_event` docstring：「点了没反应就再点一次」是真实信号）。
> 所以「多一行」的判据锚在**重放之前**那一次。

⚠️ **这条事件不改配置**：它的 `event_type` 不是 `style_config_changed`，**结构上**就不进
「配置修改频率」的分子（F41 读的是 `style_config_changed.counts_as_config_edit`），形态同 F06。
payload 里没有 `config_changed` 字段——那是 `style_config_changed` 的字段，这里不适用。

### 第 5 项 · 观察项：空检索轮占比（不判红绿）

空检索轮**不显示**这个按钮（`POST /marks` 对空 `slice_ids` 回 422）。代价是用户想标却没得标，
而这不另加埋点。记下当前占比：

```sql
select count(*) as 检索轮总数,
       count(*) filter (where payload -> 'slice_count' is not distinct from '0'::jsonb) as 空检索轮
from public.style_events
where event_type = 'retrieval_executed';
```

记下：`检索轮总数 = ___`　`空检索轮 = ___`　日期 `____`

**触发条件**：占比明显不低（比如内测里每 10 轮就有 1 轮以上）时，
「空检索轮没得标」就不再是边角情形，要回头决定是否给它一个出口。
