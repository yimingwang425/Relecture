## 二、v1 的风格空间

### 2.1 四条轴

| 轴 | 取值 | 类别 | **是否被审查执行** |
| --- | --- | --- | --- |
| 详细程度 | `P0` 30–120 / `P1` 40–90 / `P2` 25–55 / `P3` 15–40 | A | ✅ `paragraph_length` |
| 是否举例 | `more` / `fewer` | B | ❌ 仅 prompt |
| 结构 | `conclusion_first` / `buildup_first` | B | ❌ 仅 prompt |
| 深度 | `what` / `why` / `derivation` | B | ❌ 仅 prompt |

不开放的两项：`max_quote_chars` 恒 100（§12.1 合规常量）；
`chinese_ratio.min` 恒 0.85（理由见 F02）。

### 2.2 采 B 类的代价，写在前面

四条轴里**只有一条被审查执行**。其余三条进 prompt、不进判定，
即 PRD §2 的输出闭环**只覆盖 F1 采集内容的四分之一**。

这不是实现遗漏，是 §8.5 未校准的直接后果。但它必须在两个地方被显式挡住，
否则 v1.1 启用 B 类判定时会读错历史数据：

1. `style_config` 与日志中每个 B 类字段带 `enforced: false`
2. B 类字段**不进 `config_fingerprint`**（口径 F04）

### 2.3 与 X09 的辨析（会被质疑，先写清）

F3a 的 X09 给术语维度不进 prompt 的理由是
「**不该让模型花 token 做一件不计分的事**」。B 类要进 prompt，与这句话表面冲突。

两者不同：

| | 术语维度 | B 类 |
| --- | --- | --- |
| 偏好本身 | 存在 | 存在 |
| 模型能否遵守 | 能 | 能 |
| **测量状态** | **分母残缺 68%**（自动提取召回 32%） | **未校准**（§8.5） |
| 后果 | 算出来的数**无法解释** | 数**暂时不算** |

术语维度是**测量坏了**，B 类是**测量没做**。前者进 prompt 没有对应产出，
后者进 prompt 有产出（用户能感知），只是暂时无法量化。

## 三、成对比较的设计

### 3.1 六次比较，固定顺序

| # | 目标轴 | 对 | 之后 |
| --- | --- | --- | --- |
| 1 | 详细程度 | P0 vs P3 | 二分定粗档 |
| 2 | 详细程度 | P0 vs P1 或 P2 vs P3 | 由 #1 决定 |
| 3 | 举例 | more vs fewer | — |
| 4 | 结构 | 先结论 vs 先铺垫 | — |
| 5 | 深度 | what vs derivation | 二分 |
| 6 | 深度 | what vs why 或 why vs derivation | 由 #5 决定 |

落在 PRD §5.1 的「5–8 次」内。**这个数不是目标，是四条轴二分的结果。**

### 3.2 每对样例只在目标维度上不同（口径 F01）

这是**通则二的直接应用**：处理组多做的任何动作都可能在无关维度引入偏差。
若两个样例同时在「短」和「有例子」上不同，用户选了 A，
**你不知道他选的是哪一维**——而 F1 的全部产出就是这个归因。

可自动核的部分（A 类三维）写成测试；B 类只能人工核，核过的结论进样例库元数据。

### 3.3 预生成，不现场生成（口径 F02 · F03）

| 理由 | 说明 |
| --- | --- |
| **对照纪律** | 只有预生成才能在发布前人工核过「只有目标维度不同」。现场生成做不到 |
| **成本** | 现场生成每个新用户 12 次生成 ≈ $0.18，**发生在用户产生任何价值之前** |
| **延迟** | 冷启动首屏不能等两次生成 |
| **合规** | §12.1：对外展示一律用自写合成课件。F1 样例给所有用户看，等于对外展示——**这是硬约束不是偏好** |

代价：样例不是用户自己的课件，「从你的课件里选」的说服力下降。**登记，不修**。
触发条件见 §七。

素材需新写一份**合成课件片段**（约半页，有概念、有机制、可举例）。

### 3.4 P3 那一档的已知缺陷（【提出·待确认】）

交接文档 §1.6 写「P3 可以开放」，依据是成本（只贵 1.09×）。
§1.7 写 P3 的达标 **72% 来自分段**，成本臂（真实序列）上 **51/49**。

**两句话在不同的轴上。** 选了「简洁」的用户，真实使用下约一半的达标来自多敲回车，
而**审查看不见这个失败**。

三个选项：

| | 做法 | 代价 |
| --- | --- | --- |
| A | 详细程度轴止于 P2 | 用户没有「很简洁」可选，而那正是 P1 痛点方向 |
| **B（建议）** | 开放 P3，把 `total_chars` / `paragraph_count` 作为**观察项**随真实用户记录 | 零成本；内测第 1 周口径评审时读 |
| C | 把「总输出长度」判定从 v1.1 提前 | 新增一个占位阈值，与「先取证再改口径」相反 |

建议 B：**先取证，再决定**，与 F3a Q1 对 `quote_length` 的处理同形。

## 四、配置的三个标识（口径 F04）

X10 定了两个标识的分工。F1 引入 B 类后需要第三个：

| 标识 | 管什么 | B 类字段是否参与 |
| --- | --- | --- |
| `metric_set_id` | 指标集是不是同一个 | ❌ |
| `config_fingerprint` | **判定阈值**有没有变 | ❌ |
| **`prompt_profile_id`**（新增） | **prompt 侧配置**有没有变 | ✅ |

**B 类进指纹会出事**：两个 A 类判定完全相同的用户会有不同指纹，
`verify` 里「点内指纹唯一」这类守卫在真实用户数据上直接噪声化。

分开的第二个收益：以后归因「讲解质量变了，是阈值变了还是 prompt 变了」，
**一个标识答不出，两个能**。

## 五、反馈按钮 → 配置更新

### 5.1 映射（口径 F05）

| 按钮 | 映射 | 可执行 |
| --- | --- | --- |
| 太啰嗦 | 详细程度轴 **下移一格** | ✅ |
| 讲太深 | 深度轴下移一格 | ❌ 仅 prompt |
| 讲太浅 | 深度轴上移一格 | ❌ 仅 prompt |
| 例子没懂 | **见 5.2** | — |

**用离散实测点位做轴，收益不只是「测过」**：如果档位是连续区间，
「太啰嗦」必须回答「往哪个方向移多少」——**那是一个新的占位阈值**。
离散轴上就是移动一格，**零新阈值**。

### 5.2 「例子没懂」的语义此前从未定义（口径 F06 ·【提出·待确认】）

它更像「换个例子」而不是「改配置」，而 §13.2 的飞轮假定每次反馈都回写配置。
一个不产生配置变更的按钮混在里面，会让 §3.2 的
「配置修改频率首 3 次后趋近于 0」**因为按钮没接通而达标**。

建议：定义为**本轮重新生成，不改配置**，事件里 `config_changed: false`，
且**不进「配置修改频率」的分子**。

### 5.3 轴端点（口径 F07）

P3 上再点「太啰嗦」：配置不变，返回 `config_changed: false`，前端给一句说明。
**不静默吞掉**——静默吞掉会让用户以为生效了，也会让埋点里多一次假的配置变更。

## 六、交付物

### 6.1 表（Supabase）

```sql
-- 用户风格配置，一人一行
style_config
  user_id            uuid  PK  REFERENCES auth.users
  detail_level       text        -- 'P0'|'P1'|'P2'|'P3'
  use_examples       text        -- 'more'|'fewer'
  structure          text        -- 'conclusion_first'|'buildup_first'
  depth              text        -- 'what'|'why'|'derivation'
  chinese_ratio_min  numeric     -- 恒 0.85，v1 不开放
  max_quote_chars    int         -- 恒 100，合规常量
  config_version     text        -- '2.0'
  config_fingerprint text
  prompt_profile_id  text
  f1_arm             text        -- 'pairwise'|'text'（A5 的 AB 分组）
  onboarded_at       timestamptz
  created_at / updated_at
```

**RLS**：`user_id = auth.uid()`，读写各一条策略。

**不建历史表**：配置修改次数从埋点事件反推（§13 本来就要落库）。
多一张表就多一处会与事件流不一致的地方。

### 6.2 接口（FastAPI）

```
GET   /api/v1/style/config        当前配置
PUT   /api/v1/style/config        手动改档
GET   /api/v1/style/pairs/next    下一对样例（按 arm 与进度）
POST  /api/v1/style/choice        记录选择 → 返回下一对或最终配置
POST  /api/v1/style/feedback      按钮 → 配置更新
POST  /api/v1/style/from_text     对照臂：文字描述 → StyleConfig（一次模型调用）
```

**RLS 怎么连**：前端拿 Supabase JWT 传给 FastAPI，FastAPI 带该 token 访问。
**禁止用 service role key 直连**——那样 RLS 形同虚设，
而它是交接文档 §8.3 四处不能松的一处。

**API key 只在 Railway**，前端一个都不碰。

### 6.3 页面（Next.js）

| 路由 | 内容 |
| --- | --- |
| `/onboarding/style` | 成对比较，6 步，两张卡 + 进度 |
| `/onboarding/style-text` | 对照臂：一个输入框（由 `f1_arm` 决定进哪个） |
| `/settings/style` | 当前配置 + 手动改档入口 |

讲解页的反馈按钮属 F3 接线；**按钮 → 配置更新的接口是 F1 的**。

### 6.4 埋点（PRD §13.0 新增一批）

通用字段照 §13.0（含 `schema_version`）。四个新事件：

| 事件 | 关键字段 |
| --- | --- |
| `style_pair_shown` | `pair_id` · `target_dimension` · `comparison_index` · `arm` |
| `style_pair_chosen` | `pair_id` · `chosen_sample_id` · `target_dimension` · `comparison_index` · `decision_latency_ms` |
| `style_config_set` | `source`（onboarding/feedback/manual）· `changed_fields` · `config_fingerprint` · `prompt_profile_id` |
| `style_feedback_click` | `feedback_type` · `config_before` · `config_after` · **`config_changed`** |

> ⚠️ **这批 schema 是设计出来的，不是从已落盘 JSONL 反推的**——
> 与 §13.0 那四个事件的来源不同。按该节自己的原则，
> **内测第 1 周结束时须复核一次**，与 §3.4.5 的口径评审同批。

## 七、A5 的 AB 实验：本轮只建臂，不跑，且要先说清它大概率验不出来

采 B 类的主要理由就是让 A5 可验证。但要诚实登记一件事：

> **v1 目标 30–50 个真实用户，分两臂各 15–25 人。
> 任何组间比较在这个量级上都不可能有统计效力。**

按 R17，能做的只有：**同一方向在多个独立指标上重复出现**才算证据。
故预先登记读数（跑之前定死，事后不得挑）：

| 指标 | 方向 |
| --- | --- |
| onboarding 完成率 | 成对比较臂应不低于文字臂 |
| 首 3 次使用后的配置修改次数 | 成对比较臂应更低（§3.2） |
| 首会话轮次 | 成对比较臂应不低于 |

**三个指标同向才写「A5 得到支持」；只有一个同向一律写「本样本量不可分辨」，
不报显著性、不报率、只报计数。**

分组：注册时按 `hash(user_id)` 定 `f1_arm`，写死不再变。

本轮产出 PRD **§8.6**（AB 实验设计）与 **§8.7**（偏好数据建模）——
交接文档 §6「未做的三批」里 F1 那一批。

## 八、守卫清单（每条须能被反向验证变红）

通则七 #4：**把被测逻辑换成平凡实现，断言必须红。**

| 守卫 | 反向验证方式 |
| --- | --- |
| 每对样例只在目标 A 类维度上不同（F01） | 造一对在两个 A 类维度上都不同的样例 → 测试必须红 |
| B 类**不进** `config_fingerprint` | 改一个 B 类字段 → 指纹必须**不变**；改一个 A 类字段 → 必须**变** |
| B 类**进** `prompt_profile_id` | 改一个 B 类字段 → `prompt_profile_id` 必须变 |
| RLS 跨用户隔离 | 用 A 的 token 读 B 的 config → 必须 403/空 |
| B 类日志标 `enforced: false` | 去掉该标记 → 断言必须红 |
| 轴端点不越界（F07） | P3 再点「太啰嗦」→ 配置不变且 `config_changed:false`；若配置变了必须红 |
| 埋点真的写进去了 | 断言事件表行数增加，**不是断言函数被调用**——后者在写库失败时照样绿 |

最后一条是通则七 #7 的形态（59 条测试全走假模型）：
**测「调用了写库函数」和测「库里多了一行」是两件事。**
