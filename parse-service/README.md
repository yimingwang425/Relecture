# 课件解析服务（parse-service）

AI 课件讲解助手 · **F2 第一步**：把课件解析为**保留版面信息**的结构化 JSON。
对应 PRD §5.1 的 F2、§6.2 与 §10 的扫描件边界。

**只做解析。** 切片、向量化、术语提取都不在本服务范围内——接口未定时写了会返工。

| 路径 | 状态 |
| --- | --- |
| PDF（PyMuPDF） | ✅ 本次交付 |
| PPTX（python-pptx） | ⬜ schema 形状已定义并测试，解析器为下次交付 |

```
POST /parse   multipart/form-data, field=file   →  ParseResult（见 schema.py）
GET  /health
```

## ⚠️ 一、本判据的已知漏判方向与实测基础（必读）

> **这一条排在最前面，是因为它决定了本服务结论的可信范围。**

### 1.1 白字 / 裁剪路径实现的 OCR 层，本判据漏判

判据靠**不着墨文本占比**（PDF 渲染模式 Tr 3 / Tr 7）识别 OCR 文本层。
部分 OCR 工具不用 Tr 3，而是把文字**填成白色**或**塞进裁剪路径**来达到同样的隐藏效果。
**这类扫描件会被本判据放行**，OCR 噪声将一路进入切片、术语表与讲解——
正是 `测试集/SOURCES.md` 要防的那件事。

**当前无缓解手段，且刻意不造一个。** 测试集里没有这种样本，凭空调阈值等于编一个数
（PRD §3.2）。已加观测字段 `evidence.white_fill_text_ratio`（纯白填充文本字符占比），
**只记录，不接入规则，不参与任何判定**——深色底幻灯片的正常白字会让它有噪声，
实测 14.129 就有页高达 **0.919**（p13/p14），接进规则会立刻产生误判。

**触发条件**：真实用户上传中出现被放行的扫描件，或测试集补入其他 OCR 工具的产物。

### 1.2 实测基础只有 1 份文件、1 个 OCR 工具

| 项 | 现状 |
| --- | --- |
| 扫描件样本数 | **1**（`MIT15_316SU05_leader_dev.pdf`） |
| OCR 工具数 | **1**（PDF `/Producer` = `Acrobat Capture 3.0`） |
| 非扫描件对照 | 3 份，共 104 页 |
| 测量日期 | 2026-08-20 |

判据的**分离度**（间隔 0.934）在这份样本上极好，但**样本量是 1**。
一份文件证明不了「所有 OCR 工具都用 Tr 3」，只能证明「至少 Acrobat Capture 3.0 用」。
`document.producer` 字段为此保留，日后可按产出工具复盘漏判。

**扩样是本模块优先级最高的待办**，见 `TODO.md`。

### 1.3 误差方向

| 方向 | 后果 | 实测 |
| --- | --- | --- |
| **漏判**（扫描件被放行） | **危险**：OCR 噪声进入讲解 | §1.1 的白字型无法排除 |
| 误判（正常页被判扫描） | 用户丢内容，但可见可申诉 | 本测试集 **0 页** |

没有文本层的纯扫描件不构成漏判：R1 因无文本不触发，由 R2 接住判为 `image_only`，
同样 `usable=false`，效果等价。

## 二、口径决策表

> **口径变了，数字就变了。** 任何口径调整都必须**先改这张表并记录新的决策日期，再改代码**，
> 且同步递增对应的 ruleset 版本号。未记录在此表的口径变更视为 bug。
> （沿用 `实验脚本/A类规则计算脚本/README.md` 的规矩。）

### 2.1 扫描件判据（`scan_ruleset_version = scan-1.0`）

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| P01 | 判别项用什么 | **不着墨文本占比**（Tr 3 / Tr 7），不用内嵌字体数、不用图像覆盖率 | 见 §3 的实测：另两个信号的类间区间完全重叠，不可判别。OCR 工具用不可见渲染模式叠文字是**机制性特征**，不是这份文件的偶然属性 | 2026-08-20 |
| P02 | 判定粒度 | **逐页**，不整份 | 一份课件可以前 30 页是文字、后 10 页是扫描插页。整份判定会连坐 | 2026-08-20 |
| P03 | 覆盖率用并集还是最大单图 | **并集**，且先裁剪到页面内 | 扫描件可能被切成多条带（15.316 p8 是 2 张图）。不裁剪会算出 > 1.0——15.316 的扫描图右下溢出页面 | 2026-08-20 |
| P04 | 并集面积算法 | **精确**（坐标压缩 + 区间合并），不用网格近似 | 见 §4 的差异表：80×80 网格与精确值最大差 0.0125。差异虽不改变任何 kind，但让 coverage 这个佐证项带上算法噪声 | 2026-08-20 |
| P05 | 覆盖率用落版矩形还是像素尺寸 | **落版矩形** | 一张图可缩放到任意大小，像素数说明不了它占多大版面 | 2026-08-20 |
| P06 | 「无可用文本」与「扫描件」是否合并 | **不合并**：`image_only` / `empty` 与 `scanned_ocr` 分开 | 对文档的处置相同（都 `usable=false`），但含义完全不同：前者是「这页没有文字」，后者是「这页的文字是噪声」。合并会让日后复盘漏判失去依据 | 2026-08-20 |
| P07 | 白字占比是否接入规则 | **不接**，只作观测字段 | 深色底幻灯片的正常白字有噪声，实测 14.129 有页达 0.919。见 §1.1 | 2026-08-20 |
| P08 | 文档级 verdict 的取值 | **两值**：`usable_page_count == 0` → `unusable`，其余 → `usable` | 「可用页占比低于某数就拒绝上传」是把**产品决策**塞进解析层。服务的职责是如实报告哪些页不可用，**放行并告知，不替用户拒绝**。UI 文案由调用方按 `unusable_page_count` 决定 | 2026-08-20 |
| P09 | 不着墨占比用 texttrace 还是 dict 的 alpha | **texttrace 的 `type`** | 实测 `alpha == 0` 与 Tr 3 高度相关但**存在反例**（14.129 有 1 个 span 为 alpha=0 而 type=0）。且 texttrace 与 dict 的 span 切分不一致，实测仅约 **50%** 可按 origin 对齐，故**不做 span 级渲染模式回填**——页级占比以 texttrace 为准，span 级只透传原始 `alpha` | 2026-08-20 |

### 2.2 版面与邻接（`adjacency_ruleset_version = adj-1.0`）

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| P10 | 邻接给结论还是给测量 | **给测量为主**：`gap_pt` / `gap_lines` / `overlap_ratio` 与 `is_adjacent` 并排输出 | 邻接阈值应由**第三步的图注标注集**反推。现在定死等于凭空造数（PRD §3.2）。下游可用原始量自行重算，不必重新解析文件 | 2026-08-20 |
| P11 | `gap_lines` 的分母 | **主导字号**，不用块高 | 块高受行数影响：同一条图注写成一行还是两行会给出不同的 `gap_lines`，那不是我们要的信号 | 2026-08-20 |
| P12 | `overlap_ratio` 的分母 | **文本块**在正交轴上的长度，不是图片的 | 要问的是「这个块有多大比例正对着图」。一张宽图配一条短图注时，用图作分母会得到极小比值，把真图注判掉 | 2026-08-20 |
| P13 | 斜向错开的块 | `relation = null`，不构成邻接 | 两轴投影都不重叠的块与图没有版面关系，强行给一个对角距离会把满页零散文本都拉成「图注候选」 | 2026-08-20 |
| P14 | 字号信号的形式 | 绝对字号 + **`size_rank`**（本页字符加权分位） | 图注偏小、标题偏大这件事，只有在分位上才跨页面尺寸与跨课件可比。本测试集就有 805×621 / 792×611 / 720×540 三种页面尺寸 | 2026-08-20 |
| P15 | 块级字体汇总是否取代 span | **不取代**，span 列表完整保留 | 块是 PyMuPDF 按几何聚类出来的，一块混多字号很常见（22.081J p3 同一块里 13.06pt 与 31.33pt 并存）。只留汇总会把标题与副标题压成一个平均字号，字号信号就废了 | 2026-08-20 |
| P16 | 块的 `order` 是否是阅读顺序 | **不是**，schema 里显式声明 | PDF 无可靠阅读顺序，`sort=True` 只是几何排序（先 y 后 x），多栏版面下与人的阅读顺序不一致。声明清楚，免得下游当成阅读顺序用 | 2026-08-20 |

### 2.3 契约（`schema_version = 1.0`）

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| P17 | 两种来源的信息如何容纳 | 共有信息升顶层，格式特有信号收进按 `kind` 区分的 **`origin` 可辨识联合** | 不为了「统一 PDF 与 PPTX」而丢任一侧的字段。丢掉版面信息会导致第三步整个返工 | 2026-08-20 |
| P18 | 未知字段 | **严格报错**（`extra="forbid"`） | 静默忽略意味着字段名拼错也能跑通，等实验跑完才发现用的是默认值 | 2026-08-20 |
| P19 | 字体解析失败的表示 | `resolved=false` + 各属性为 `null`，**不填默认值** | 下游必须能区分「没加粗」与「不知道有没有加粗」。PPTX 的 run 常继承自 layout/master，这一区分在 PPTX 路径上是刚需 | 2026-08-20 |
| P20 | 图片二进制 | **不导出**，只给 `image_id` + `bbox` + `pixel_size` | 图注通道要的是位置关系不是像素。需要像素时按 `image_id` 回取，接口另开 | 2026-08-20 |
| P21 | 演讲者备注 | 进 `page.notes_text`，**不进 `blocks`** | 备注没有 bbox，混进 blocks 会污染邻接计算。**备注同样受 PRD §12.1 的单段引用 100 字上限约束**，下游引用其原文时须与正文同等对待。术语提取是否使用备注由第三步决定，本服务**只存不用** | 2026-08-20 |
| P22 | PPTX 母版图片 | `origin.from_layout` 标记，**不参与邻接计算** | 每页都有的 logo 会把每个文本块都判成「图注」。（模型已定义，解析器下次交付） | 2026-08-20 |

## 三、判据为什么不是「内嵌字体数 ≈ 0 且有铺满版面的全页图」

在 4 份 OCW 课件共 **123 页**上实测，原判据的两个信号**都不可判别**。

### 3.1 「铺满版面」不可判别

| 类别 | n | min | p50 | max |
| --- | --- | --- | --- | --- |
| 扫描页（15.316 的 17 个有文本页） | 17 | **0.775** | 0.810 | **0.844** |
| 非扫描页 | 106 | 0.000 | 0.141 | **0.865** |

**非扫描侧的最大值高于扫描侧的最大值，区间完全被包住。** 落在扫描页区间里的数字文本页：

| 页 | 并集覆盖率 | 不着墨占比 | 实际是什么 |
| --- | --- | --- | --- |
| 14.129 p32 | 0.865 | 0.066 | 满版示意图 + 标题 |
| 14.129 p12 | 0.830 | 0.025 | 满宽配图 + 标题 |
| 14.129 p45 | 0.823 | 0.043 | 满宽配图 + 标题 |
| 14.129 p46 | 0.788 | 0.032 | 同上 |

机制原因：**扫描图有白边**。15.316 的扫描图落版矩形 `(53.2, 75.2)–(805.9, 621.0)`
在 `805×621` 的页面上右下溢出、左上留边，只覆盖 0.82，够不到「铺满」；
而讲义里贴一张满宽配图同样能到 0.8+。

### 3.2 「内嵌字体数 ≈ 0」不可判别

123 页中 **45 页**内嵌字体数为 0，其中仅 19 页属扫描件——**精确率 42%**。

| 文件 | 内嵌字体为 0 的页 | 是否扫描件 |
| --- | --- | --- |
| MIT15_316SU05_leader_dev | 19 / 19 | 是 |
| MIT14_129S25_lec02 | 21 / 50 | 否 |
| MIT11_201F07_slides2 | 4 / 15 | 否 |
| MIT22_081JF10_lec01b | 1 / 39 | 否 |

原因：**base-14 标准字体按 PDF 规范本就不内嵌**。11.201 全篇用未内嵌的
`ArialMT` / `TimesNewRomanPSMT`，是彻头彻尾的数字课件；而 15.316 的 OCR 层用的是
`Helvetica` / `Times-Roman`——**与之属同一类未内嵌标准字体**，这一路根本分不开。

### 3.3 不着墨文本占比可判别

| 类别 | n | 不着墨占比 |
| --- | --- | --- |
| 15.316 的 17 个有文本页 | 17 | 全部 = **1.000** |
| 其余 104 个有文本页 | 104 | 中位 0.000，**最大 0.066** |

**间隔 `[0.066, 1.000]`，宽 0.934。**

这两条结论都已钉成回归测试（`tests/test_corpus.py::TestScannedDetection`），
任何把 coverage 或字体数当判别器的改动都会让测试变红。

## 四、网格近似 vs 精确并集

方案评审阶段的探针用 **80×80 网格**近似求图像并集面积，实现改用**精确扫描线**后
coverage 会变。差异**不静默吸收**，逐页列出：

```
python -m scripts.probe_corpus --compare-grid
```

| 项 | 值 |
| --- | --- |
| 受影响页数（\|差值\| > 1e-4） | **80 / 123** |
| \|差值\| 最大 | **0.0125**（14.129 p34：0.7631 → 0.7506） |
| \|差值\| 均值 | **0.0039** |
| 因此改变判定的页 | **0** |

差异全部落在 ±0.013 以内，而 coverage 在判据里只作**佐证项**且阈值 0.50 距实测下界
0.775 有 0.275 的余量——0.013 的抖动不可能翻转任何一页的 kind。
但这不构成「可以不管」的理由：coverage 会随解析实现变动这件事必须记录在案，
否则日后有人拿探针值与实现值对不上时无从解释。

**golden file 只对 `kind` 做回归，不含 coverage。** 浮点几何量换算法就会在末位变动，
写进 golden 会让每次几何改动都红一片，反而掩盖真正的判定漂移。

`python -m scripts.probe_corpus`（语料：`实验脚本/测试集/`）

| 文件 | digital_text | scanned_ocr | image_only | empty | verdict |

| MIT11_201F07_slides2.pdf | 15 | 0 | 0 | 0 | usable |

  判为不可用**正确**——它们确实没有可讲解的文本。

## 六、开发

```bash
python -m venv .venv && ./.venv/bin/pip install -e ".[dev]"
./.venv/bin/python -m pytest                        # 全部测试
./.venv/bin/python -m scripts.probe_corpus          # 语料验证报告
./.venv/bin/python -m scripts.probe_corpus --write-golden --compare-grid
./.venv/bin/python -m parse_service.schema > schema.json   # 导出 JSON Schema 供 TS 侧生成类型
./.venv/bin/uvicorn parse_service.app:app --reload
```

**解析耗时实测**：11.201 5.1 ms/页、22.081J 7.2 ms/页、14.129 70.3 ms/页（228 张图）、
15.316 125.1 ms/页（大图解码）。最慢一份 50 页共 3.5 s——上传环节这个量级
不需要任务队列，接口同步返回。

### 模块

| 模块 | 职责 |
| --- | --- |
| `schema.py` | **契约的唯一定义处**。pydantic 模型，可导出 JSON Schema |
| `geometry.py` | 矩形、精确并集、邻接度量。不依赖任何解析库，两条来源路径共用 |
| `scanned.py` | 扫描件判据。**不 import PyMuPDF**——输入是数字，可脱离文件单测与重算 |
| `pdf.py` | PyMuPDF 路径：只负责把数字取出来，不含判据逻辑 |
| `app.py` | FastAPI `POST /parse` |
