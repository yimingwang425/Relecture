## 二、F1 的产品决策（本轮拍板）

### 2.1 风格空间：四条轴，只有一条被执行

| 轴 | 取值 | 类别 | 被审查执行 |
| --- | --- | --- | --- |
| 详细程度 | `P0` / `P2` / `P3`（**P1 已退出**，见 F23） | A | ✅ `paragraph_length` |
| 是否举例 | `more` / `fewer` | B | ❌ 仅 prompt |
| 结构 | `conclusion_first` / `buildup_first` | B | ❌ 仅 prompt |
| 深度 | `what` / `why` / `derivation` | B | ❌ 仅 prompt |

**采 B 类是明确决策，代价已登记**：输出闭环只覆盖 F1 采集内容的四分之一。
两处机制挡住它被误读——B 类字段带 `enforced: false`，且不进 `config_fingerprint`。

不开放：`max_quote_chars` 恒 100（合规常量）、`chinese_ratio.min` 恒 0.85（F03，P4 口径未收敛）。

### 2.2 成对比较：固定顺序 6 次

```
#1 详细程度  P0 vs P3     选 P0 → #2 P0 vs P2 → 结果 P0 或 P2
                          选 P3 → #2 P2 vs P3 → 结果 P2 或 P3
#3 举例      more vs fewer
#4 结构      conclusion_first vs buildup_first
#5 深度      what vs derivation
                          选 what → #6 what vs why
                          选 derivation → #6 why vs derivation
```

**不做主动选题**（后验估计 + 信息增益）：4 轴 / 6 次没有可选的，触发条件是维度数或预算显著变大。

### 2.3 反馈按钮（F05–F07）

| 按钮 | 行为 |
| --- | --- |
| 太啰嗦 | 详细程度轴下移一格（**P0→P2→P3**，不再经过 P1） |
| 讲太深 / 讲太浅 | 深度轴下移 / 上移一格（仅 prompt） |
| 例子没懂 | **不改配置**，只触发本轮重生成，`config_changed: false`，不进「配置修改频率」分子 |
| 轴端点 | 配置不变 + `config_changed: false` + 前端给一句说明，**不静默吞掉** |

### 2.4 A5 的 AB 实验：只建臂，不跑，且已预先登记读数

30–50 用户分两臂各 15–25，**任何组间比较在这个量级上都不可能有统计效力**。
预先登记（跑前定死，事后不得挑）：onboarding 完成率 · 首 3 次配置修改次数 · 首会话轮次。
**三个指标同向才写「A5 得到支持」；只有一个同向一律写「本样本量不可分辨」，不报显著性。**

## 三、阶段 1 · 表与 RLS

**交付**：`supabase/migrations/20260907120000_f1_style_config.sql`（唯一 DDL 出处）·
`verify_rls_prod.py`（生产正向）· `verify_rls_local.mjs`（本地反向，PGlite）

**表**：`style_config` 一人一行。刻意不存 `chinese_ratio_min` / `max_quote_chars`（常量）、
三个标识（Python 侧现算）、配置历史表（从埋点反推）、delete 策略（注销走 cascade）。

**AB 分组在数据库里算**（F08）：`auth.users` after-insert 触发器 + `md5(uid)` 首位二分。
不能由前端做——前端算 hash 是「TS 一份 Python 一份必然漂」的复发，且用户对自己那行有
update 权限，**能改自己的臂**。不用 `hashtext()`（PostgreSQL 不承诺跨大版本稳定）。

**验收 17 绿**。这一阶段最重要的两个发现：

- **F11 · 原验收是空转的。** 任务书写的「A 读 B 的行 → 返回空」在 B 的行不存在时也绿、
  整表被收权时也绿。故每条「拒绝」断言旁边必须有一条「允许」反向控制。
  同一条里还有：「A 冒名 insert → 报错」测的是主键不是 `with check`
  （RLS 关掉后错误码从 `42501` 变 `23505`，**照样报错、断言照样绿**），改成断错误码。
- **F14 · §12.1「注销即清空」此前是一条从未被测量过的承诺。** 它写进隐私政策、
  靠外键 cascade 实现，但没人验过它会触发。补了 cascade 断言 + 反向验证。
  推论：§12.1 其余各条（一键删除、异议处理留档）落地时同样要各配一条会红的断言。

**插入理由**：阶段 1 的验收是从本地 Python 打 PostgREST 跑的——数据库层验了，

**交付**：`web/`（`/login`、`/`、`/debug/rls`）· 构建期护栏 · Playwright 回归工具。

### 撞出来的坑（全部是「配置错了不报错，只是安静地不工作」）

| # | 坑 | 处置 |
| --- | --- | --- |
| 1 | GitHub 主邮箱从学校换成个人后，**仓库里所有用旧邮箱的历史提交全部不可归属**，Vercel 静默拦部署。归属是按账号当前已验证邮箱**实时**算的，不是提交时冻结 | F15。检查查的是 `gh api` 的 `author.login`（Vercel 反查的同一个信号），**不比对写死的邮箱**——比对常量的版本在那次事故里会是绿的 |
| 2 | 改 Root Directory **不会自动触发部署** | 人工核对项 |

| 4 | **删 git 分支不删 Vercel 部署**——部署带着自己的 URL 和 `NEXT_PUBLIC_ENABLE_DEBUG_ROUTES=1` 继续活着，而看起来已经清理完了 | 人工核对项 |
| 5 | **「preview 19 绿」跑的是 `f5cbab6`，不是以为的 `5bd6d23`**——后者构建失败，分支别名停在上一个成功的部署上 | F17 |

### 三条口径

- **F15 · 部署的前置条件要有断言。**
- **F16 · 判据要有分辨力。** 起因：全局搜 `sb_secret_` 会永远命中护栏自己的源码，
  判据从此不可用；`service_role` 更隐蔽（旧版 key 是 JWT，`service_role` 在 base64 载荷里，
  **明文一个字看不到**——恰好是危害最大的那个）。改成形态匹配：
  `sb_secret_[A-Za-z0-9_-]{20,}`、JWT 解载荷看 role。
  **读「产物 0 命中」之前先验判据自身**：护栏源码必须 0 命中、真 key 形态必须命中、
  `filesScanned > 0`——扫了 0 个文件也会得到 0 命中。
- **F17 · 先核对读的是哪个对象。** 部署自报 `x-build-commit`，回归工具第 0 组先核对它。
  期望 commit **必须显式传入**（取本地 HEAD 会在「本地领先于部署」时静默通过，
  正是那次的情形）；拿不到 commit **判失败不跳过**；值缺失时不设这个头而不是填 `unknown`
  （占位会让比对永远相等或永远不等，两种都不是判据）。

> F17 比 F15/F16 更根本：那两条是「配置错了不报错」，这条是「**读数对了但读的不是那个对象**」
> ——前者错在环境，后者错在验收本身。

## 五、阶段 2 · 样例资产

**交付**：`f1_samples/synthetic_deck.md`（10 页 / 1129 词 / 23 块，英文，Bloom filter）·
`pairs.json`（8 对 16 样例）· `verify_pairs.py` · `manual_review.md` + `manual_review_result.md`

**核对**：22 绿 0 红 · 16/16 过生产 `a_rules` 判定 · 隶属集合全对 · 反向验证 8 条全绿 ·
**人工核 8 对全通过** · 累计 95 次调用 / $2.40。

### 5.1 这一阶段最重要的一条：F18

> **样例必须由模型在对应 `StyleConfig` 下真实生成，不得手写、不得人工润色。**
>
> 手写会得到「理想中的 P3」，而用户拿到的是「模型在 P3 下实际产出的」。两者不同，
> 用户按样例选完拿到的就不是他选的那个——**F1 的整个前提垮掉**。

F19 是它的延伸：**模型、采样参数、以及 prompt 形状**全部取生产侧唯一出处。
（F19 初版只覆盖了前两项，「唯一出处」四个字只兑现了一半，而后面那次误判正落在这个缺口上。）

### 5.2 P1 退出（F23）

`detail_p0_p1` 连续 8 次生成都过不了判据。不是运气，是结构性的：
**P1(40–90) 完全被 P0(30–120) 包含**，且 `points.py` 对 P1 的定语就是
「自然中枢仍在区间内，只是余量收窄」——**P1 被设计成模型不必改变行为就能满足的轻微偏离**，
那它作为用户档位就不携带信息。第 4 次尝试里 P1 甚至比 P0 更长，方向是反的。

产品侧后果才是关键：A 类指标分不开，很难相信用户分得开——那次点击更像噪声而非偏好，
**而 F1 的全部产出就是这个归因**。

> 连带的一般结论：**`AXIS_POINTS` 是为配置扫描实验设计的点位，不是为产品档位设计的。**
> 扫描要覆盖参数空间，产品要用户可分辨，两个用途对点位的要求不同。
> F1 复用了这些点位而没检查用途可否迁移——这是又一次「前提变了句子没变」。

对照：新对 `detail_p0_p2` **第 1 次生成即通过**。

### 5.3 发现 A：提出后被自己撤销（P3 可达）

生产判定补进核对后，P3 连试 11 次 0 达标，换第二份课件复现仍 0/4——
**按当时的决策规则本该判 P3 不可达并删掉这个档位**。动手前多查一步，结论反了：

| 条件 | P3 达标 |
| --- | --- |
| 扫描实验落盘数据，**首次尝试**（未经重生成） | **33/54** |
| 生产 `build_system` 装置（实测 n=4） | 2/4 |
| 自拼 system 模板（累计 n=19） | 1/19 |

同模型、同参数、同 `StyleConfig`。**不可达的是装置，不是 P3。**
生产 `SYSTEM_TEMPLATE` 把风格要求放在角色行之后，课件走每轮 user turn；
自拼模板把 2500 字英文课件放最前面、风格要求垫在最后。

而那条差异**是阶段 2 开头自己登记过的代价**，解释反常结果时没想起来。

**F26 · 宣布「模型做不到 X」之前，先查项目自己已落盘的数据里 X 有没有做到过。**
代价不对称——一个「做不到」的结论会直接删掉产品功能，而查一次落盘数据只要几分钟。
两个实例的形态相同，都是**候选列表列漏**而不是推理出错：
第一次漏了「装置」，第二次漏了「文本内部的引用结构」。已落盘的数据不受这份列表限制，
这正是它该被先查一遍的原因。

### 5.4 装置对齐生产（重生成两轮的原因）

最终装置按落盘的 450 个真实切片对齐：

| | 真实检索（n=90 轮 / 450 片） | 本样例 |
| --- | --- | --- |
| 每轮片数 | 恒为 5（X03 的 B=5） | 5 |
| 每片字符 | 中位 271 · 范围 60–433 | 256–400 |
| 每轮合计 | 中位 1161 · 四分位 1128–1498 | 1502 |

**F28 · 「我在扮演检索器」单独编号，方向写明**：与「不经检索」不是同一件事——
不经检索是少了一个环节，**扮演检索器是用一个乐观的替身冒充那个环节**，后者更危险，
因为它看起来把环节补上了。真实检索会带回不相关片、会漏关键片、会命中互相矛盾的片，
人工挑的 5 段一种都没有。**方向：样例的上下文质量是真实使用时的上界。规模像不等于质量像。**
