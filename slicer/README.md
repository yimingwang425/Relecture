# 课件切片（slicer）

AI 课件讲解助手 · **F2 第二步 2a**：把解析结果切成检索用的切片。

**只做切片。** 向量化与 embedding 供应商选型是 2b，不在本库范围内。

**这是库，不是服务。** 纯函数 `ParseResult → SliceSet`，无 I/O、无模型调用、
不写盘、不缓存——所有持久化走 Supabase。

```python
from parse_service.pdf import parse_pdf
from slicer import slice_document

parsed = parse_pdf(data, "lecture.pdf")
slices = slice_document(parsed)            # split_threshold_chars 由 2b 注入
```

实际调用方是 `api/api/ingest.py`（摄入：parse → slice → 组文本 → 嵌入 → 落库）。
分层单向无环：

```
parse_service.schema   契约，无依赖
        ↑
     slicer            消费契约
        ↑
api.ingest             编排
```

> 2026-10-07：原来的编排层 `parse_service.app`（独立的 `POST /parse` 服务）与它的
> `parse_service.response` 已删除——2026-09-11 起解析并进了 `api/`，那个服务不再部署，
> 而它是一个**无鉴权**端点。S19 那条「切片不单开端点」的理由在 `api/` 里照样成立。

安装（两个包互为本地兄弟，都不发布到 PyPI，故彼此不写进 `dependencies`）：

```bash
python -m venv .venv
./.venv/bin/pip install -e ../parse-service -e ".[dev]"
./.venv/bin/python -m pytest
./.venv/bin/python -m scripts.report_corpus     # 切片结果报告
```

### 1.1 切片单位与边界

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| S01 | 切片单位 | **页（幻灯片）**，一个可用页 = 一个切片 | **实测依据**（2026-08-20，4 份 OCW 共 100 个可用页）：每页字符 p50 = 266、p95 = 1132、**max = 1917，无一页超 2000**。幻灯片版面本身限制单页信息量，页天然有界——「切片多长」因此是**测量结果**而非需要现在拍板的**输入参数**。另见 S02/S03 的排除理由 | 2026-08-20 |
| S02 | 为什么不用固定 token 窗口 | 不用 | 幻灯片文本**非线性**：标题、项目符号、图注在版面上并列而非连续，拼成字符串再切会在任意位置断开（实测 37.9% 的块 ≤ 20 字符）。重叠窗口的价值是「避免切断连续论述」，而幻灯片本来就是断的，重叠只是复制文本抬高 2b 成本。且它要求**现在**就定窗口大小与重叠比例两个无依据的数，而这两个数取决于 2b 还没选的 embedding 供应商 | 2026-08-20 |
| S03 | 为什么不用块 | 不用 | 块 p50 仅 **30 字符**，单个 bullet 脱离标题后无法讲解；向量库规模膨胀 **7.4×**（741 块 vs 100 页），2b 成本随之翻倍；且召回后仍要拼回页才能生成讲解，等于绕一圈 | 2026-08-20 |
| S04 | 过短页是否合并 | **不合并**。改为输出 `prev_slice_id` / `next_slice_id` 邻接链，检索层需要上下文时自行扩展 | 合并阈值**无依据**（凭感觉给数）；且合并会切断「切片 ↔ 页」的一一对应，而那正是溯源文案「第 N 页」的基础。「是否需要合并」应由数据回答，不由直觉回答。**本条由 `方案.md` §1.4 提出，评审确认采纳**——记此归属是因为它是一条「先不做」的决定，日后若被推翻，需要能查到当初为什么不做。⚠️ 原定的验证计划已知不可行，见 [`TODO.md`](TODO.md) | 2026-08-20 |
| S05 | 超长页拆分 | 按**块边界**拆，绝不在块中间拆。阈值 `split_threshold_chars` 为**注入参数，默认 `None` = 不拆** | 块是作者给的最小语义单位，拆穿它就回到 S02 的老问题。阈值**占位待定**：取决于 2b 选定的 embedding 供应商的上下文窗口，本层不写死。当前语料 **0 触发**（max 1917） | 2026-08-20 |
| S06 | `page_indices` 的形状 | 恒为列表，v1 恒为单元素 | 给日后可能的过短页合并留形状，避免届时改契约 | 2026-08-20 |

### 1.2 溯源与版面

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| S07 | 溯源粒度 | **块**（`SliceUnit`） | **实测依据**：页（100 条）太粗——只能定位到页，不知引用来自哪段，一页 7 个块人工标不准；span（1951 条、**39.7% ≤ 3 字符**）太细——对用户无意义、标注不可行。块 741 条、p50 = 30 字符，是唯一同时满足「可做最长公共子串比对」「有 bbox 可高亮」「人工可标注」的粒度 | 2026-08-20 |
| S08 | `text_span` | 记录每块文本在 `slice.text` 中的 `[起, 止)` 偏移 | PRD §12.1 的「单段引用 ≤ 100 字」要与课件原文求最长公共子串，靠它把命中片段回指到具体的块。**这一步顺带解掉了 A 类脚本 TODO 里挂着的「引用长度与课件原文比对」**——那条卡在「需课件文本作为额外输入」，触发条件写的正是「接入 F2 之后」 | 2026-08-20 |
| S09 | span 是否进切片 | **不进**。需要时按 `content_sha256` + `block_id` 回 parse 结果取 | 块级已含 `size_pt` / `size_rank` / `bold` / `bbox` / `image_adjacency`，第三步图注通道要的全在这一层。span 1951 条是纯体积成本。**前提**：parse 结果必须持久化，切片只是它的派生视图——若 parse 结果用完即弃，span 就真丢了 | 2026-08-20 |
| S10 | 版面信息 | `bbox_pt` / `bbox_norm` / `font` / `image_adjacency` 全部原样透传 | 第三步的图注通道要用 bbox 与 adjacency。切片若只吐文本，第三步得回头重做整个解析 | 2026-08-20 |
| S11 | 是否输出 `role` 分类 | **不输出**（title / body / caption / footer 一概不给） | 图注判定属**第三步**。切片层贴标签等于用无依据的阈值抢做第三步的决定，而第三步真做时还得先把错标签清掉。实测佐证：22.081J 上 `is_adjacent` 命中 18/334 块，抓到真图注的同时也命中了 `REAL HEAT ENGINES`（`size_rank` 0.96，是图**上方的标题**）——**单靠邻接会误收，须与 `size_rank` 联合判断，那正是第三步该做的事**。已有测试 `test_no_derived_labels_emitted` 防止以后有人顺手加上 | 2026-08-20 |
| S12 | `title_block_id` 的选取 | `size_rank` 最高，并列取最靠上者。**无阈值** | 只需相对比较（哪个最大），不需要「够不够大才算标题」的绝对判断——那会引入一个无依据的数。实测在 22.081J 上给出的正是幻灯片标题（rank 0.94–0.97） | 2026-08-20 |

### 1.3 页号与不可用页

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| S13 | 不可用页 | `scanned_ocr` / `image_only` / `empty` **不产出切片** | OCR 噪声与空页进检索只会污染召回 | 2026-08-20 |
| S14 | 页号编排 | **一律用原始页号**，跳过的页表现为 `page_indices` 的**缺号**。绝不重新编号 | 重编会让「第 N 页」对不上用户手里的课件，用户按页码翻会翻错页。实测 14.129 跳过 p33–p36 后，切片页号为 30, 31, 32, **37**, 38 | 2026-08-20 |
| S15 | `skipped_pages` 的内容 | 页号 + `kind` + `reason` + `image_count` + `image_coverage_union` | **`image_only` 的页不是空页，是「内容全在图里」的页。** 用户问到这类内容时检索会一无所获，而 PRD §10 现有的兜底文案是「这个内容课件里没有提到」——**那句话是错的**：课件提到了，只是我们读不了图。正确文案应为「这部分在第 N 页的图里，我读不了图」。本字段就是让 F3 能写出这句话的数据 | 2026-08-20 |
| S16 | 可用页但无文本块 | 也进 `skipped_pages`，`reason` 标为异常 | 理论上不该出现（解析的 R3 会判成 `empty`）。真出现了也不能产出空切片——空切片会污染检索 | 2026-08-20 |

### 1.4 【评审指定】合规与架构

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| S17 | 文档主键 | **本库不产出文档主键。** `content_sha256` 仅用于确认与 parse 结果同源 | 【评审指定】PRD §12.1 承诺「课件仅存于用户个人空间，**不跨用户共享、不建公共库、不做跨用户检索**」。按内容哈希做主键或去重键，等于两个用户上传同一份课件时共用一份存储，直接违反该承诺。**这是产品承诺，不是性能取舍**，不因存储成本而放宽。主键归持久化层：随机 id 或 `(user_id, content_sha256)`。全局切片键为 `(document_id, slice_id)`，`slice_id` 只是文档内局部 id | 2026-08-20 |
| S18 | `page_signals` 透传 | 每切片带 `image_coverage_union` 与 `text_char_count`，**不做任何判定、不生成任何标签** | 【评审指定】`digital_text` 里存在「标题 + 满版图 + 图注」的页（如 22.081J p21 `REAL HEAT ENGINES`），文本仅几十字符但**实质内容在图里**；PRD §8.1 实测图注术语在图密集章节占分母 **83–87%**。这两个量是 2b 之后按召回率分组统计的依据，也是 S04 的判据来源。**现在没有数据，故不拍任何阈值**——只把量带下去 | 2026-08-20 |
| S19 | 持久化 | 本库不写盘、不缓存；服务侧亦然，全部持久化走 Supabase | 【评审指定】理由是合规：PRD §12.1 的「一键删除」与「注销即清空」若跨两个存储系统实现，会有**两处漏点**。由此切片不单开端点——`POST /parse` 一次返回解析结果与切片，由调用方一次性写入 | 2026-08-20 |

### 1.5 计量口径 ⚠️ 2b 必读

| 编号 | 口径 | 决策 | 理由 | 决策日期 |
| --- | --- | --- | --- | --- |
| S20 | 块间拼接分隔符 | **单个换行 `"\n"`**（`slicer.core._JOIN`） | 幻灯片的块是版面上**并列的独立条目**，用空格拼会把标题与第一个 bullet 连成一句话。⚠️ **这是一条可能要调的口径**：`slice.text` 会**原样进 embedding**，分隔符影响嵌入向量。若 2b 选定的模型对换行敏感（或更适合 `"\n\n"` / Markdown 列表标记），此处需要改——改则必须递增 `SLICE_RULESET_VERSION`，且已入库的向量全部失效需重算 | 2026-08-20 |
| S21 | `char_count` 的含义 | **拼接后的字符数**，`len(slice.text)`，**含块间分隔符** | 与「各块文本长度直接相加」不是同一个数：差值 = 块数 − 1。实测 100 个切片：min +0、p50 **+6**、max **+30**。见 §2 的口径差异说明 | 2026-08-20 |
| S22 | `char_count` **不是 token 数** | ⚠️ **超长页拆分（S05）按上下文窗口判定时，不可直接用 `char_count`** | 字符与 token 不是固定比值：本语料为英文，char/token 通常在 3–4 之间，而**中文课件会完全不同**（汉字约 1–1.5 字符/token）。本产品的目标用户是跨语言学习者（PRD §4.1），两种语言的课件都会遇到。**2b 必须用选定供应商自己的分词器实测**，不要用固定比值换算，更不要把 `char_count` 当 token 数直接与上下文窗口比较 | 2026-08-20 |

## 二、口径差异：过短切片是 17 页，不是方案里写的 18 页

`方案.md` §0 记的是「字符量 < 120 的页 **18**」，实现后的报告是 **17**。
差异**不是解析变化，是计量口径不同**：

| 口径 | 定义 | 值 |
| --- | --- | --- |
| 方案探针 | 各块文本长度**直接相加** | 18 页 < 120 |
| 实现（`char_count`） | 拼接后的长度，**含块间换行** | 17 页 < 120 |

`char_count` 恒 ≥ 探针值，差值 = 块数 − 1（实测 p50 = +6，max = +30）。
跨越 120 边界的**只有一页**：

| 文件 | 页 | 块文本和 | `char_count` | 块数 | 差 |
| --- | --- | --- | --- | --- | --- |
| MIT22_081JF10_lec01b.pdf | 25 | 116 | **120** | 5 | +4 |

同一原因下 `char_count` 的最大值也从探针的 1911 变成 1917。
**「无一页超过 2000」这个结论不受影响**，S01 的实测依据仍然成立。

记录此条的理由与 `parse-service/README.md` 的「网格近似 vs 精确并集」一致：
**口径变动导致的数字变化必须显式记录，不能静默吸收**——否则日后有人拿方案里的
18 与报告里的 17 对不上时，无从判断是口径问题还是解析回归。

### 17 个过短切片（`char_count` < 120）按图像覆盖率的构成

| 分组 | 页数 | 占比 | 页 |
| --- | --- | --- | --- |
| 覆盖 = 0（纯目录 / 讨论页） | 2 | 12% | 11.201 p6、22.081J p38 |
| 0 < 覆盖 < 0.2 | 2 | 12% | 14.129 p39、p43 |
| 0.2 ≤ 覆盖 < 0.5 | 6 | 35% | 14.129 p9/p15/p23/p44/p48、22.081J p33 |
| **覆盖 ≥ 0.5（实质内容很可能在图里）** | **7** | **41%** | 14.129 p12/p13/p14/p32/p45/p46/p47 |

这个构成本身就是 S04（不合并）的支撑：覆盖率 0.866 的 14.129 p32（标题
`The Evolution of Ecosystems…`，57 字符）与覆盖率 0.000 的 11.201 p6
（`Planning history in global`，101 字符）**长度相近但性质完全相反**——
前者是「内容在图里，文字只是标题」，后者是「这页本来就没多少内容」。
按长度把它们塞进同一个桶去合并，会同时做错两件事。
