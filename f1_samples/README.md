**这是生产资产，不是实验产物**——所以不在 `实验脚本/` 下。
`explain` / `retrieval` 在运行时读这里的 `pairs.json`，而不是反过来。

| 文件 | 内容 |
| --- | --- |
| `README.md` | **F1 口径决策表**（下 §一），全项目唯一一份 |

**结尾一段「……没有涉及××，需要补充材料」**。为消它试了两次，**两次的机制假设都错**：

| | 假设 | 预测 | 实测 |
| --- | --- | --- | --- |
| 第 1 次（评审） | 材料太少 → 模型觉得不够 | 喂得越少抱怨越多 | 方向不成立 |
| 第 2 次（我） | 文本内部前向引用（counting variant） | 引用出页则归零 | **没归零** |

判据在重生成前写死（口径 F29），基线也在重生成前量过：

| | 基线（503 词整份喂） | 现在（10 页 / 喂 5 片） | 预期 |
| --- | --- | --- | --- |
| **A · 片段表述** | 9/16 样例 · 15 处 | 13/16 · 26 处 | 基本不变 → **反而升了** |
| **B · 缺口抱怨** | 15/16 样例 · 32 处 | **12/16 · 16 处** | 归零 → **没有** |

**抱怨的内容变了，行为没变。** 旧版全部指向 counting variant（一处前向引用）；
新版指向「最优 `k` 值怎么选」「删除操作」——**模型从被喂的推导式推断出下一步该讲
什么，发现没给**。更糟的是**新出现的一类**（事后诊断指标，与 B 分开报）：

- 引用**喂过的**页（1/2/4/5/7）做溯源：**16/16** ← 生产要的行为，正确
- 点名**没喂过的**页（第 3 页、第 6 页）：**4/16** ← 新用户不可理解

页号来自 `build_user_turn` 的溯源行（生产刻意要的）。喂 1/2/4/5/7 就等于告诉模型
3 和 6 存在且没给——**它数了一下**。这不是幻觉，是如实报告。

**结论：这件事与课件设计无关。** 两次分别从「加长」和「去前向引用」两个方向改，
都没消掉；变的只是抱怨指向什么。**杠杆在 X06 本身或在 UI**，不在素材上——
而这正是我最初列的两个选项，绕了两圈回到原点。**登记，不自行处理。**
阶段 3 需拍板：

| | 做法 | 代价 |
| --- | --- | --- |
| A | 样例场景关掉 X06 那一节 | 装置又与生产分叉——刚花两轮修好的那个坑（F19） |
| B | UI 上截掉结尾段 | 用户看到的不是模型的完整输出，样例与真实讲解再次不一致 |
| C | 接受 | 8 对样例共享一段近乎相同的结尾，稀释用户要比较的风格差异 |

**拍板（2026-09-09，阶段 3 开工前）：选 C —— 接受现状 + 页面文案解释。** 立为口径 **F30**。

理由是另两条各自动了不该动的东西：A 让样例装置再次与生产分叉，正是 F19 花两轮修好的坑；
B 让用户看到的不是模型的完整输出，F18 要防的那件事（「按样例选完拿到的不是他选的那个」）
以弱化形式回来。C 的代价（共享结尾稀释风格差异）**登记，不修**。

落地：`/onboarding/style` 每屏样例下方常驻一句话——样例是模型在一份**示例课件**的片段上
真实生成的，片段是节选，所以结尾常出现「这部分没有涉及××」、偶尔点到没给出的页码，
**那是讲解助手在如实说明它手里有什么，与用户自己的课件无关**。
一句话同时解释了预注册的 B（缺口抱怨）和事后诊断的那一类（点名未喂页），
因为对用户来说这两件事是同一个观感。

### 未验证项 · P2 与 P3 用户能否分辨（登记，不处理）

三对里 P2 vs P3 的字/段差值最小（12.7 字，另两对 19.9 / 16.6）。P0/P1 那次的教训
是「指标分不开 → 用户大概也分不开」，同一个问题在 P2/P3 上**同样未知**。
本阶段不处理——它要么随发现 A 一起消失（P3 若下线，这对就不存在），
要么在 P3 站住之后单独验。

### 发现 B · P0 与 P1 在档位轴上分不开 —— **已拍板：P1 退出**

`detail_p0_p1` 那一对**连续 8 次生成都没过隶属集合判据**。这不是运气：

| 尝试 | P0 字/段 | P1 字/段 | 隶属集合 |
| --- | --- | --- | --- |
| 1 | 85.7 | 57.7 | 都是 `{P0, P1}` |
| 2–3 | *（当时没逐次记数，只记了红/绿）* | | 都是 `{P0, P1}` |
| 4 | 76.0 | **81.1** | 都是 `{P0, P1}` |
| 5 | 66.1 | 65.7 | 都是 `{P0, P1}` |
| 6 | 63.6 | 70.8 | 都是 `{P0, P1}` |
| 7 | 86.4 | 69.8 | 都是 `{P0, P1}` |
| 8 | 72.2 | 65.1 | 都是 `{P0, P1}` |

**结构性原因**：`P1(40–90)` 完全被 `P0(30–120)` 包含，而模型在这两条指令下的
自然段落长度都落在 40–90 里。这与项目自己的先验一致——`scan/points.py` 给 P1 的
定语就是「**自然中枢仍在区间内**，只是余量收窄」。P1 被设计成一个模型不必改变行为
就能满足的轻微偏离，那么 P0 与 P1 的输出长得像，是这个设计的**直接推论**而不是意外。
第 4 次尝试里 P1 甚至比 P0 更长（81.1 vs 76.0），方向都是反的。

**产品侧的后果**（这才是要紧的那一半）：onboarding 的第 2 次比较，
在用户第 1 步选了 P0 之后给他看 P0 vs P1。如果 A 类指标分不开这两个样例，
**很难相信用户分得开**——那次点击拿到的更像噪声而不是偏好。而 F1 的全部产出
就是这个归因（F01）。

**拍板结果（2026-09-09）：P1 退出用户可选档位。** 不是「第 2 次比较跳过 P1」——
是这条轴从四档变成**三档 `P0 / P2 / P3`**，因为「P1 存在但从不被比较」是个说不通的状态。

| 项 | 变更 |
| --- | --- |
| 详细程度轴 | `P0 / P1 / P2 / P3` → **`P0 / P2 / P3`** |
| 比较 #2 | `P0 vs P1` → **`P0 vs P2`** |
| 比较次数 | **仍是 6**（二分不受影响：#1 选 P0 → #2 `P0 vs P2`；选 P3 → #2 `P2 vs P3`） |
| 反馈按钮「太啰嗦」（F05） | 沿 **`P0 → P2 → P3`** 下移一格；轴端点仍按 F07 不静默吞掉 |
| 隶属集合判据 | 改按**产品档位**遍历，不再包含 P1（口径 F23） |

`detail_p0_p2` 新对**第 1 次生成即通过**（P0 63.3 / P2 50.8，集合 `{P0}` vs `{P0,P2}`），
两侧都过生产判定——与 P0/P1 试 8 次全败形成对照，说明问题确实出在 P1 这个点上。

⚠️ **`style_config` 表的 CHECK 仍允许 `P1`**（阶段 1 建表时四档都在）。现在没有任何
写入路径会产生 P1，留着无害；改 CHECK 与 F05 的映射一并在阶段 3 做，见 §二。
