## 三、已拍板的产品决策（不要重新讨论）

### 3.1 事件表 `user_id` 存**真 uuid**，不存 hash

PRD §13.0 原文要求事件表存 hashed user_id。**这条现在改**：

- 库内存真 uuid，挂外键到 `auth.users`，`on delete cascade`
- hash 放在**导出层**（对外导出数据时才 hash）

理由：§13.0 的目的是防止事件数据被关联到个人，而 §12.1「注销即清空」是更强的保障——
数据都没了，hash 与否无所谓。存 hash 却挂不上外键、cascade 失效，
等于**拿一个弱保障换掉一个强保障**。F14 刚把「注销即清空」从一条从未被测量过的承诺
变成有断言的，不能在事件表上把它丢掉。

**要做的连带修改**：改写 PRD §13.0 措辞，改成
「事件数据对外导出时 hash；库内以真 uuid 存储，受 RLS 保护并随账号注销级联删除」。
改完在 `F1进度.md` 未决项 #4 标记已解决并注明依据。

### 3.2 成对比较**一步一个事件**，不是只记最终结果

代价是数据量 ×6（30–50 用户 × 6 步 ≈ 几百行，不是问题）。
换到的是：**弃流点可见**（onboarding 完成率是 A5 预登记的三个指标之一，
只知道完成率不知道卡在哪等于没法改）、**位置效应可算**（否则 `left_variant` 白记）。

### 3.3 事件数从四个改为**五个**

「四个 `style_*` 事件」是方案设计期的数字，一步一事件会撑破它。
`F1进度.md` §二 已登记「这批是设计出来的不是从落盘数据反推的」——现在就是反推的时候。
五个事件见 §四。

### 3.4 `prompt_profile_id` 落在 Python 侧，但**不建 FastAPI**

F04 要求三个标识分工，`metric_set_id` / `config_fingerprint` 已在 Python 侧，
第三个必须同处，否则就是「TS 一份 Python 一份必然漂」（F13 / 约束 3）的复发。

但**现在不建 FastAPI**。关键事实：`prompt_profile_id` 只在**分析时**被消费，不在写入时。所以：

- Python 侧现在就写这个模块（算法的唯一出处，与另两个标识同处）
- **事件里存构成它的原始字段**：B 类三条轴的取值 + prompt 模板版本
- 分析时由 Python 从原始字段算出 id

TS 从头到尾不碰这个算法，也不需要每写一条事件就发一次网络请求。
FastAPI 推迟到 F2 接线时再建——那时它是真需要的，现在建等于为一个函数
启用整条 Railway 部署链 + 多一条 §13.3 出境记录 + 多一道接缝。

### 3.5 v1 走**邀请制**，不做自助注册页

`/login` 只有登录没有注册入口，这是内测的硬阻塞——没有用户就收不到任何埋点数据。

30–50 人规模下邀请制比注册页省得多：不用做邮箱验证流程、找回密码、防滥用。
具体形态见 §4.5。

### 3.6 事件表用**一张表 + `event_type` 列**，差异字段放 `payload jsonb`

五个事件共享 `user_id` / `arm` / `session_id` / 时间戳，RLS 策略与 cascade 完全一样。
拆五张表意味着同一条 RLS 写五遍、cascade 断言写五遍，**而它们必然一起改**——
这正是 F13「同一份东西多处出处必然漂」的形态（F33 已为取值域立过一次护栏）。

**代价与必须配的护栏**：`payload` 是 jsonb，没有 schema 约束。
因此**每个 `event_type` 的必需字段必须有一条会红的护栏**——
例如 `style_pair_shown` 的 payload 缺 `left_variant` 即判红。
这条不能省，否则 jsonb 就是个什么都能塞的口袋，而漏字段不会报错。

### 3.7 `dwell_ms` 只采集不判读

**算法定死**：从该步渲染完成到点选，取 `performance.now()` 差值。
切走标签页**不扣除**，但**同时记 `hidden_ms`**（`visibilitychange` 累加页面不可见时长）。
只记一个总数的话，「读了 40 秒」和「挂着 40 秒」永久混在一起，事后分不开。

**v1 不设阈值，不做任何「乱点」判定。** 我们没有任何先验知道读完一段 400 字讲解要多久，
现在拍一个数字是瞎猜。判读标准等内测第 1 周数据落盘后单独立一条口径，
**且立的时候要写明这条线是怎么来的**。

这是 F29 的直接应用：观察项的判读标准跑之前写死，事后不得按结果重划分类。
拿到数据再按分布划线，等于用结果定义判据。埋点代码里**不要出现任何毫秒阈值常量**。

## 四、本阶段要做的

### 4.1 事件表 `style_events`

一张表，结构按 §3.6。约束：

- `user_id` 真 uuid + 外键 `auth.users` + `on delete cascade`（§3.1）
- 公共列：`user_id` · `event_type` · `arm` · `session_id` · `created_at`
- 差异字段进 `payload jsonb`
- RLS：用户只能 insert 自己的事件，**不能读、不能改、不能删**
  （读事件是分析行为，走 service_role，不给客户端）
- 沿用 `20260907120000_f1_style_config.sql` 的写法风格
- **payload 必需字段护栏**（§3.6）：五个 `event_type` 各自的必需字段缺一即红

### 4.2 五个事件

字段以下面为准。**取值一律从已有模块读**，不在埋点代码里另写一份常量（F13）。

| 事件 | 何时触发 | 必须包含 |
| --- | --- | --- |
| `style_pair_shown` | 成对比较每一步渲染时 | `step`（1–6）· `axis` · `pair_id` · **`left_variant`** · `arm` |
| `style_pair_chosen` | 每一步点选时 | 同上全部 + `chosen_variant`（**存档位，不存左右**）· `dwell_ms` · `hidden_ms`（§3.7） |
| `style_onboarding_completed` | 收尾屏落库成功后 | `arm` · 四条轴最终取值 · `steps_completed` · 总耗时 |
| `style_text_mapped` | 对照臂分类返回后 | **`call`（model/effort/thinking/max_tokens）** · 哪几条轴来自描述 / 哪几条回落默认 · `ok` · **不记描述原文** |
| `style_config_changed` | 设置页改轴 或 点反馈按钮 | 改前值 · 改后值 · `trigger`（手动改／哪个反馈按钮）· **`config_changed`**（F06/F07：例子没懂与轴端点为 `false`） |

三处硬要求：

1. **`left_variant` 与 `chosen_variant`**：选择记档位不记左右（位置随机后只有档位稳定），
   但 `left_variant` 必须一起记，否则位置效应事后分离不出来——这正是阶段 3 做位置随机化的目的。
2. **`call` 必须从 `web/lib/style/text-arm.ts` 读**，不在埋点里写第二份。
   它一变两条臂的对照关系就变了，而事后从数据里看不出来。
3. **`config_changed` 必须与 `web/lib/style/feedback.ts` 的返回同源**，
   不在埋点里重新判断——F06 要求「例子没懂」不进「配置修改频率」的分子。

### 4.3 `prompt_profile_id` 的 Python 模块

与 `metric_set_id` / `config_fingerprint` 同处、同风格。**只写函数，不建服务**（§3.4）。
输入是事件里存的原始字段，输出是 id。

### 4.4 反馈接口

`/settings/style` 的四个按钮目前是前端直改 `style_config`。本阶段接上事件写入。
**行为不变**（F05–F07 已在阶段 3 验收通过），只加埋点。

### 4.5 邀请制：`scripts/invite_user.mjs`

用 service_role key 调 Supabase 的 `auth.admin.createUser`
（即后台 Add user 那个动作的脚本版）。参数：邮箱 + 密码 + `email_confirm: true`。

**不要直接往 `auth.users` 插 SQL 行**——那会绕过 Supabase 自己的密码哈希与字段初始化，
属于绕开人家的机制自己造一套。

**service_role key 只在本地 `.env`，绝不进 Vercel 环境变量。**
它绕过全部 RLS，进了前端环境等于把整个数据库开放出去。
**这条要加进构建护栏**（沿用 F16 已有形态：把真 key 形态注进构建环境后扫产物，仍须 0 命中）。

记录谁被邀请了：脚本每次追加一行到 `docs/F1/invited_users.md`（邮箱 + 日期 + 用途）。
**不要建表**——建表就要管 RLS、管 cascade，而这是一份 30 行的运维记录，不是产品数据。

不做注册 UI。

## 五、验收纪律（前四阶段共同得出，继续适用）

- 每条「拒绝」断言配一条「允许」反向控制
- 断错误码 / 错误文本，不断「有没有报错」
- 判据自身先验一遍分辨力（空表上的绿、护栏源码自己命中，都是空转）
- 先核对读的是哪个对象（`x-build-commit`；期望值显式传入，不取本地 HEAD）
- 判据与基线在跑之前定死，事后不按结果重划
- **断言「库里多了一行」而不是「函数被调用」**——本阶段尤其适用，
  埋点最容易写成「调用了 track() 就算绿」

本阶段特有的两条：

- **事件表 cascade 必须有断言**（F14 的形态）：建账号 → 写几条事件 → 删账号 →
  事件行必须也没了。少了它，§12.1 在事件表上又变成一条没被测量过的承诺。
- **`left_variant` 与 `call` 必须有「真的落进库里」的断言**，不是「代码里传了这个字段」。
  这两处是本阶段唯一会让前一阶段工作白做的地方。
