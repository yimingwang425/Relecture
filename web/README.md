## 〇、部署前提（三条，全都是「配错了不报错，只是安静地不工作」）

这三条不在代码里，改代码永远修不好它们。共同形态是**通则六**：
不报错，只是结果与你以为的不同——而你看到的东西**看起来完全正常**。

| # | 前提 | 配错时的表现 | 有没有断言 |
| --- | --- | --- | --- |
| 1 | 提交作者邮箱是 GitHub 上**已验证**的邮箱 | Vercel 反查不到账号，**静默拦下部署** | ✅ `npm run verify:identity` |
| 2 | 改完 Root Directory 要**手动 Redeploy** | 改了设置以为生效了，**跑的仍是上一次构建** | ❌ 只能人工核 |
| 3 | Framework Preset 必须是 **Next.js** | 建项目时根目录没有前端 → 被判成 `Other`；**改 Root Directory 不会重新判定**，于是按静态站构建，路由全 404 | ❌ 只能人工核 |
| 4 | Vercel 的 **Include files outside the Root Directory** 保持开启（阶段 3 新增） | 关掉时 `next build` **直接失败**：`Module not found: ../../../f1_samples/pairs.json` | ⚠️ 构建自己会红 |

第 2、3 条 2026-09-08 都实际踩到了。它们的共同点值得单独说一句：
**Vercel 的自动判定只在建项目那一刻发生一次**，之后你改的任何设置都不会让它重算。
「我改了设置」和「设置生效了」之间隔着一次手动 Redeploy，而中间没有任何提示。

第 2、3 条没有自动断言——它们是 Vercel 控制台的状态，本地查不到。
**如实登记为人工核对项，不写成「已验证」**（通则七 #1）。
可查的代理信号：部署后访问 `/login` 应返回 200 而不是 404；
返回 404 且构建日志里没有 Next.js 的路由表，基本就是第 3 条。

### 1 · 提交作者邮箱必须是 GitHub 上已验证的邮箱

**否则 Vercel 静默拦下部署。** 拦下的表现是「什么也没发生」：代码没问题、
构建根本没跑、没有一条错误指向这里——你会以为自己在看新版本，其实看的是上一次部署。
通则六的形态。

2026-09-08 实际踩到：GitHub 主邮箱从学校邮箱换成个人邮箱、学校邮箱被移除，
而仓库的 `user.email` 还是老的。

**归属是按账号当前的已验证邮箱实时算的，不是提交时冻结的。** 所以换邮箱之后，
历史上用旧邮箱的提交会一起变成不可归属——新提交不受影响，
但**回滚或重新部署那些提交会撞同一堵墙**。当时「能过」不等于现在还能过。

```bash
npm run verify:identity                    # 推完跑一次
npm run verify:identity -- --allow-offline # 没有 gh 时显式放行
```

查的是 `gh api repos/…/commits/<sha>` 的 `author.login`——**Vercel 反查的同一个信号**，
不是比对一个写死的邮箱。比对常量的版本在这次事故里**会是绿的**：邮箱没变，
变的是「GitHub 还认不认它」。一个在事故发生时照样绿的检查就是没有检查。

反向控制是一个已知反查不到账号的历史提交（`3c7ffba`，作者是已被移除的学校邮箱）：
它每次都必须返回 `null`，否则说明读到的不是活信号，「HEAD 可归属」那条也就不成立。

没有 `gh` 时默认**判失败**，要放行必须显式加 `--allow-offline`——
一个跳过了却仍然退出 0 的检查，与它防的那个失败是同一类东西。

想更早拦住，可以挂成 hook（本仓库没有自动装，改的是你的 git 配置）：

```bash
printf '#!/bin/sh\ncd web && npm run --silent verify:identity\n' > .git/hooks/pre-push
chmod +x .git/hooks/pre-push
```

## 一、两条构建期护栏

### 1 · `NEXT_PUBLIC_*` 里不许有 secret key

判定在 [`lib/public-env-guard.mjs`](lib/public-env-guard.mjs)，**构建期与运行期共用同一份**，
不各写一份。构建期那条是主的：等到运行期才发现，`NEXT_PUBLIC_` 的值已经被内联进
bundle 了——泄露在第一个访客打开页面时就已经发生。

只 `includes("service_role")` 是不够的。**旧版 legacy service key 是一个 JWT**，
`service_role` 这个词在 base64 载荷里，明文一个字都看不到：

```
eyJhbGciOiJIUzI1NiJ9.eyJyb2xlIjoic2VydmljZV9yb2xlIn0.xxx
                     ^ 解开才是 {"role":"service_role"}
```

所以护栏会解 JWT 载荷看 `role`。危害最大的那个恰好是字面量扫不出来的那个。

**只扫 `NEXT_PUBLIC_` 前缀。** 不带该前缀的变量留在服务端、不进 bundle，
在那里放 secret 是正常用法（阶段 3 的模型 API key 就该在那儿）。一起拦掉会让这条
护栏在阶段 3 变成障碍，然后被关掉——**一条会被关掉的护栏等于没有护栏。**

### 2 · `/debug/rls` 是构建期开关，不是运行期 404

文件名是 `app/debug/rls/page.debug.tsx`。只有 `NEXT_PUBLIC_ENABLE_DEBUG_ROUTES=1` 时，
`debug.tsx` 才在 `next.config.ts` 的 `pageExtensions` 里，这个模块才成为一条路由。

用 `notFound()` 的版本里路由**仍在构建产物中**、页面代码仍被打包，防护取决于一个
运行期分支没被绕过。这里是连模块都不编译进去。**Vercel 生产环境不配这个变量即为关。**

### 3 · 构建产物里不能有真实凭据（口径 F16）

前两条查「环境变量里有没有」，这条查「**最后打出来的东西里有没有**」——
源码里硬编码一个 key，前两条一个字都看不见。

**判据是形态匹配，不是搜字符串。** 人工验收时在 devtools 里全局搜 `sb_secret_`
有 3 处命中，查下来全是护栏自己的源码（`v.startsWith("sb_secret_")` 这类字面量比较）。
这让「搜到 0 处」这个判据**永久失效**：以后任何人搜都会命中它们。当天还能人工分辨，
是因为只有 3 处且都在一个文件里——**真泄露的时候是第 4 处，混在里面看不出来。**

所以：

| 判据 | 为什么不误伤护栏源码 |
| --- | --- |
| `sb_secret_[A-Za-z0-9_-]{20,}` | 源码里 `sb_secret_` 后面跟的是引号，长度 0 |
| JWT 形态 → **解载荷看 `role`** | 源码里的 `"service_role"` 是裸字符串，不构成 JWT |

`20` 有依据：实测本项目 publishable key 在前缀之后有 31 个字符，
取 20 两侧都有余量——低于任何真实 key 的熵段长度，又远高于字面量后能跟的字符数。

**读「产物 0 命中」之前，先验判据自身的两条性质**（`verify:build-guards` 里已断言）：
护栏源码必须 0 命中、真 key 形态必须命中。少了任何一条，那个 0 都不说明问题。

### 验证

`npm run verify:guards`：便宜的单元用例覆盖判定分支，**三次真实 `next build`** 覆盖接线。

单测全绿只证明那个函数会算，证明不了 `next.config.ts` 真的调了它——F3a 那次
59 条测试全绿而 `AnthropicModel.request_signature` 被批量改名一条没红，就是这个形态
（通则七 #7：这个对象被哪条断言碰过？）。

| 断言 | 反向 |
| --- | --- |
| `NEXT_PUBLIC_TEST_KEY=sb_secret_fake` → 构建失败，且报出变量名 | — |
| 旧版 service_role JWT → 构建失败 | 用例本身断言了它**不含明文** `service_role`，否则测的是字面量分支 |
| 干净的 env → 构建成功 | 证明护栏不是「永远失败」 |
| 关掉开关 → 产物里没有 `/debug/rls` | 打开开关 → 有。否则「没有」可能只是这页编译不过 |
| `.next` 里 0 命中真实凭据 | **把一个 key 形态的串写进源码、真的构建一次**，扫描必须红。不用「塞进 `NEXT_PUBLIC_` 变量」——那条路在构建期护栏处就失败了，根本产不出产物，而源码硬编码正是环境变量护栏看不见的那条路 |
| 扫描确实读到了文件（`filesScanned > 0`） | 目录写错时命中数同样是 0，那种「0 命中」什么也证明不了 |

## 一·五、阶段 3 新增的两条护栏

### 4 · 四条轴的取值域三处一致（口径 F33）

`npm run verify:axes`。取值域住在三个地方，**而且不可能合并成一处**：

| 出处 | 为什么非有不可 |
| --- | --- |
| `f1_samples/style_axes.py` | 生成/核对样例的脚本读它 |
| `supabase/migrations/*.sql` 的 CHECK | 数据库自己执行，不信任应用层 |
| `lib/style/axes.ts` | 浏览器跑不了 Python，也读不到 CHECK |

漂了**不会报错**：前端拒绝的取值数据库照收，或者用户点一下按钮拿到一个 `23514`。
护栏把三份解析出来逐项比对，外加 `pairs.json` 的档位是否还在取值域里（共四方）。

**CHECK 按时间戳取每列的最后一次定义**——`20260907120000` 那份写的仍是四档（历史，不回改），
`20260909130000` 收紧成三档，护栏读到的是后者。

判据自身先验过两条性质：每个解析器断言非空条数（**解析失败得到三个空对象，比对同样会绿**），
以及一条反向控制——往 TS 里混一个 `P1`，比对必须变红。

### 5 · 反馈映射与比较树（F05 / F06 / F07）

`npm run verify:logic`。这三条口径都是「**没做某件事**」型的语义，页面上看不出来：

- **F05** 详细程度沿 `P0 → P2 → P3` 移动，**跳过 P1**。少一格多一格在界面上都只是「档位变了」。
- **F06**「例子没懂」不改配置、**且不计入**「配置修改频率」的分子。接错了的表现是
  §3.2 的指标**因为按钮没接通而达标**——一个自己会变绿的指标。
- **F07** 端点不静默吞掉：配置不变，但必须有一句说明。吞掉与正常处理在库里的痕迹完全相同。

外加 64 条比较路径穷举、16 个样例真渲染、以及一条 HTML 转义断言。

还有两组「一处出处」的**接线**断言（通则七 #7：这个对象被哪条断言碰过？）：

- **对照臂的模型与参数**必须从 `lib/style/text-arm.ts` 取，`route.ts` 里不许有硬编码的
  模型 id——发出去的和记进埋点的漂开之后，**事后从数据里看不出来**。
- **左右随机**：`makeFlips` 两个分支都可达（注入可控 rng 各钉一次），且组件确实用的是
  那个被测函数。写成 `rng() < 0` 时位置会恒定，而**页面看起来完全正常**。

纯 TS 模块用项目已有的 `tsc` 编成 CommonJS 再 require，**不引入 `tsx` / `ts-node`**——
为一个测试脚本加一条供应链不划算。编译产物落在 `node_modules/` 下而不是系统临时目录，
因为编出来的 `markdown.js` 要 `require("react/jsx-runtime")`，`/tmp` 下解析不到。

## 二、`/debug/rls` 为什么把两个查询放在同一次渲染里

它同时显示「查自己」和「查 `?probe=<uuid>`」的行数。分两次页面加载去查的话，
「读不到 B」就有第二种解释：**会话在两次之间过期了**。并排渲染后两个查询共享同一个
JWT、同一次请求周期，前者是后者的反向控制——缺了它后者什么也证明不了
（通则七 #5，与 `supabase/verify_rls_prod.py` 的步骤 1 同形）。

## 三、两处容易踩的地方

**`proxy.ts` 不是 `middleware.ts`。** Next 16 起 `middleware` 约定已废弃。
导出的函数名必须叫 `proxy`——**只改文件名不改函数名，它不会被调用，而构建不报错**，
表现是「会话再也不刷新了」，几十分钟后用户被登出，没有一条日志指向这里。

**`lib/supabase/server.ts` 里有一个 `catch {}`**，是全站唯一一处刻意的静默吞。
被吞的不是「一次失败的写入」而是「一次不必要的写入」：Server Component 里
`cookies()` 只读，写必然抛；真正的会话刷新在 `proxy.ts`，那里可写、失败会暴露。
**删 `proxy.ts` 之前先读那段注释**——删掉之后这个吞才会变成真的丢失。

## 四、已知没有覆盖到的

**阶段 3 的三个页面没有浏览器级自动断言。** `verify_browser.mjs` 仍只覆盖阶段 1.5 的
`/`、`/login`、`/debug/rls`——新页面都要登录态，扩它需要部署 + 测试账号。
**刻意没有写一段没跑过的自动化**：那种代码会以「已验证」的样子存在，比没有更糟。
人工清单在 `docs/F1/F1进度.md` §五。

**对照臂的真实调用已在人工验收里跑通，但分类质量没有金标准。** 跑通 ≠ 分对：
只验过一条描述（「讲细一点」→ 详细程度来自描述、其余三轴显式标「没提到」），
模型把描述映射错的概率**未测**。

**503（缺 key）那条分支本轮未复验**：环境已配上 key，恢复未配置状态要再部署两次。
上次验过的构建是 `a8670b1`，措辞正确。

**`left_variant` 与 `call`（model/effort）目前没有事件表可落。** 前者在页面 DOM 与组件状态里，
后者在响应体与服务端日志里。**阶段 4 必须把两者收进事件**，否则这次随机化与一处出处都白做。

`proxy.ts` 的**会话刷新行为本身没有断言**。它只在 access token 接近过期时才做事，
而验收全程都在 token 有效期内。这里如实登记，不写成「已验证」——
凡是写成「已验证」的句子必须能指出是哪次测量（通则七 #1）。

### 跑回归工具前先核对读的是哪个构建（口径 F17）

```bash
npm run verify:browser -- --base https://… --commit <该部署对应的 sha>
```

`--commit` **必须显式给出，工具不会去取本地 HEAD**。取本地 HEAD 会让检查在
「本地领先于部署」时静默通过——2026-09-08 就是这个情形：分支最后一个 commit 的
preview 构建失败，别名停在上一个成功的部署上，而报告写的是「preview 19 绿」。
**读数是真的，读的对象不是我以为的那个**（通则七 #6）。

部署自报的方式是响应头 `x-build-commit`（`next.config.ts` 的 `headers()`，
值取 `VERCEL_GIT_COMMIT_SHA`）。三个设计点各有理由：

| 设计 | 换成别的会怎样 |
| --- | --- |
| 期望值显式传入 | 取本地 HEAD → 事故当时会绿 |
| 拿不到该头即**判失败** | 跳过 → 退出 0 的假绿 |
| 值缺失时**不设**该头，不填 `unknown` | 填占位 → 比对永远相等或永远不等，两种都不是判据 |

工具里还有一条反向控制：拿一个伪造 sha 走同一段比对逻辑，必须判为不匹配——
否则「相等」可能只是因为比对恒真。
