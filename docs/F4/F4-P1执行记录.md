## 二、三个探查结论（任务书要的三条自述）

### 1. `round_id` 的来源 —— **本轮之前没有，现在服务端生成**（口径 F65）

查过 `/explain` 响应的每一个字段。**没有任何稳定的轮标识**，而两个看起来像的都不能用：

| 候选 | 为什么不行 |
| --- | --- |
| `retrieval.signature` | 它只认**提问 + 命中切片**（`ContextPack.signature()` 的定义）。同一个人把同一个问题问两遍会得到**同一个值** —— 拿它当幂等键，第二轮的标记会被幂等成第一轮的，而表现是「点了没反应」 |
| `session_id` | 它是整场会话（一次页面加载），不是一轮 |
| `request_signature` | 有，但 `RoundResult` 里的它没有进响应；且它含 system 与 messages，注入一旦发生它就变了 —— 一个会被自己改变的标识 |

处置：`/explain` 里 `str(uuid.uuid4())`，随响应返回 `round_id`，前端原样带回来。
**一次 `/explain` = 一轮**；轮内由审查驱动的重生成不新开一个（它们在同一次
`run_round` 里，本来就共用这一个 id），与 PRD §13.0「轮 = 用户可见的一次输出」一致。

### 2. `slice_ids` 有没有落库 —— **有，但「非空」没有护栏**

`retrieval_executed.payload.slice_ids` 从阶段 6 就在，而且每项带 `document_id`
（`events.py` 的 `_slice_identities`）。所以任务书说的「没有 → 补上」不适用。

**但发现了一个真的洞**：`f1_event_payload_ok` 判的是「键在不在」，
而**空数组 `[]` 完全通过它**（不是 SQL NULL、不是 JSON null、不是空字符串）。
于是「检索命中了 5 片，而事件里的 slice_ids 是空的」**没有任何东西会红** ——
而那正是护栏指标「重复提问率」的唯一数据来源（口径 F62），漏了补不回来。

补了两层，形态与 `20260913090000` 那条 `deck_id` 不变量相同：
- 数据库：`f4_event_slice_ids_ok` + `style_events_slice_ids_ok` CHECK；
- Python：`events._slice_ids_problem`，构造时就抛。

⚠️ **空检索是例外，放行**（`slice_count = 0`）。一片都没检索到是合法状态，
而且它**更该**被采集到（PRD §6.2：空检索是显式失败，比答非所问安全）。
一并拒掉就是口径 F50 那条教训的复发。

⚠️ 这条能做成 DB CHECK、而上传那两个字段只能留在 Python 侧，差别在于：
这四个讲解事件由服务端发，`/explain` 把 `record_events()` 的结果原样放进响应的
`events` 字段 —— **被 23514 拒掉的事件在这里不是静默消失的**。

### 3. 一处**偏离任务书**的地方：`slice_ids` 是 `text[]` 不是 `uuid[]`（口径 F66）

任务书与 F4 方案 §3.1 都写 `uuid[]`。**切片的身份本来就不是一个 uuid**：
`slices` 的主键是 `(document_id uuid, slice_id text)`，后者是文档内局部 id，
而 2026-09-12 的真库观测记着「一门课的两份讲义都有 `s001`」。

`uuid[]` 只有两条出路，都是坏的：

| 写法 | 后果 |
| --- | --- |
| 存 `document_id` | 粒度退化成**整份讲义**：标记一页 → 这份讲义以后每次命中都注入。**恒触发**，而恒触发的限定语最难发现（输出看起来完全正常，只是每轮多讲一句） |
| 只存 `slice_id` | 它不是 uuid，写不进 `uuid[]`；硬转 text 又会让 A 讲义的 `s001` 与 B 讲义的 `s001` 撞成同一个身份 —— **误触发，且不可见** |

处置：`text[]`，元素是 `'<document_id>:<slice_id>'`，唯一拼法出处
`api/api/marks.py` 的 `slice_key()`（两段里出现分隔符就抛）。
`&&` 与 GIN 在 `text[]` 上一样用。已登记为口径 F66。

### 顺手修的一处（在本轮范围内，说明理由）

`pipeline.run_round` 原本调了**两次** `build_user_turn`：一次拼要发出去的消息，
一次拼要记进 `trajectory` 的历史。两次恰好等值，所以此前看不出问题。
`turn_prefix` 一进来它们就不再等值 —— **历史里会缺那句限定语**，
于是下一轮模型看到的历史与它上一轮真收到的不同。改成只拼一次、两处共用。

## 七、如实登记的四件事

1. **路径前缀不一致。** `POST /api/v1/marks` 带 `/api/v1`，而 `/explain`、`/courses`、
   `/me/style` 都不带。这是任务书写死的路径，照做了。**不在本轮顺手统一** ——
   统一要动前端已经在调的三条路由，那是一次与 F4 无关的改动，而它失败的样子是「页面白屏」。
   **触发条件**：真要加版本前缀时一次性全改，那时 v1 的路由表还只有五条。

2. **走替身检索的那条路（不传 `course_id`）标记不了。** `InMemoryRetriever`
   没有 `document_id`，产不出身份键，`slice_keys` 是空的，而 `POST /api/v1/marks`
   拒绝空 `slice_ids`（一条空 mark 与任何一轮都不相交，是一行死数据）。
   **给 P2**：`slice_keys` 为空时不要显示那个按钮；`/explain` 响应里
   `confusion.skipped_reason` 会说明原因。这不是缺陷 —— 替身讲的是合成课件（口径 F02）。

3. **`insert_mark` 的 23505 假正文里那句 `message` 是编的。** 本表还没在真库上撞过一次。
   它无害的理由是匹配条件**只认错误码 + 调用点**，不认正文里的任何字符串
   （`insert_document` 那次教训），并且有一条断言专门钉住这一点：
   正文里连约束名都没有时仍然要翻译成功。
   **待办**：`verify_f4_marks.py` 第一次真跑撞上时，把真正文抄回 `test_marks.py`。

4. **`count_marks()` 是把行读回来数长度**，不是 `Prefer: count=exact`（那个数在响应头里，
   而 `_get` 只交出 body，改它的返回形状会波及每一个既有调用点）。
   v1 一个账号最多几十行，代价可忽略。**触发条件**：内测里有账号上到几百条时。
