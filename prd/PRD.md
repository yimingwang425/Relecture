## 1. 背景与问题定义

### 1.1 现状

用 AI 辅助学习已成为学生默认行为，其中「上传课件让 AI 讲解」是最高频用法之一。该行为目前发生在通用对话框（ChatGPT / Claude / Gemini）中。

### 1.2 问题

通用对话框不是为「持续的、有个人偏好的学习」设计的。实际使用中反复出现同一循环：

```
调教风格 → 短暂好用 → 逐渐失效 → 烦躁地新开对话 → 重新调教
```

观察来源：项目发起人本人及同学群体的真实学习场景。在同学中该现象为普遍现象，且伴随明确的负面情绪与替代行为（新开对话）。

### 1.3 为什么现在做

- 该行为已高频发生
- 模型能力已足够，瓶颈在产品层而非模型层
- 通用对话框厂商短期内不会为单一垂直场景做深度个性化

## 2. 痛点拆解

2个独立问题，解法不同，需分别对待。

| 编号 | 痛点 | 本质 | 对应解法 |
| --- | --- | --- | --- |
| P1 | 找不到适合自己的讲解风格；能感知模型教学语言不适但**说不出为什么以及怎样改变** | 交互设计问题 | 从「描述」改为「选择 + 反馈」 |
| P2 | 对话变长后风格漂移，需反复提醒 | 长上下文结构性问题 | 独立风格审查 agent |

**P1 是最核心的洞察**：让用户「描述想要的风格」这个交互本身是失败的。大部分用户很难用语言描述自己的认知习惯，但**一定能在两个样例之间选出更舒服的那个**。

本产品构建三个闭环：

| 闭环 | 内容 | Project 为何做不到 |
| --- | --- | --- |
| 入口闭环（P1） | 样例选择替代文字描述 | 无此交互形态 |
| 输出闭环（P2） | 生成后检查，不合格则重生成 | 无法在生成与展示之间插入步骤 |
| 反馈闭环 | 用户点击反馈 → 配置自动更新 | 无反馈回写通道 |

## 3. 目标与成功指标

### 3.1 北极星指标

周活跃用户的平均会话轮次

理由：该指标同时反映"用户愿意用"和"讲解质量足够好以至于用户愿意继续问下去"。若风格不合适，用户会提前放弃。

### 3.2 过程指标

| 指标 | 基线 | v1 目标 | 说明 |
| --- | --- | --- | --- |
| 风格遵循度（20 轮后） | 待实测 | ≥ 85% | 核心质量指标，定义见 §8 |
| 风格配置修改频率 | — | 首 3 次使用后趋近于 0 | 反映风格习得是否准确 |
| 溯源率 | 待实测 | ≥ 90% | 讲解内容可追溯到课件片段的比例 |
| 次周留存 | — | ≥ 30% | 真实用户 |
| 单会话成本 | 待实测 | < $0.05 | 见 §9 |

### 3.3 非目标（v1 不追求）

- 盈利与商业化验证
- 用户规模（目标 30–50 名真实用户即可）

## 4. 用户与场景

### 4.1 目标用户

核心画像：对学习质量有明确要求的大学生，尤其是跨语言学习者（如英文授课但中文思考的留学生）。

关键限定：对讲解质量无感知的用户不是目标用户——他们不会察觉风格问题，因而不会有使用动机。这一限定必须写明，否则会误判市场规模。

### 4.2 典型场景

| 场景 | 频次 | 说明 |
| --- | --- | --- |
| S1 · 课后当周消化 | 每周 1–2 次 | 刚上完课，理解本周课件 |
| S2 · 期中/期末复习 | 季节性高峰 | 集中过多周内容 |
| S3 · 卡在某个概念 | 不定期 | 针对性提问 |

## 5. 需求范围

### 5.1 v1 做

**F1 · 风格获取**
- 首次使用：用同一段课件内容生成 3–4 种风格样例，用户选择
- 持续校准：每次讲解后提供快捷反馈按钮（太啰嗦 / 例子没懂 / 讲太浅 / 讲太深）
- 配置以结构化参数存储，非自然语言描述（这是可程序化检查的前提）

**F2 · 课件上传与处理**
- 支持 PDF / PPT
- 切片、索引，供检索使用

**F3 · 讲解对话**
- 基于检索到的课件片段生成讲解
- 每次输出经风格审查后才呈现给用户

**F4 · 跨会话记忆**
- 风格配置跨课程、跨会话继承
- 记录用户标记为"没看懂"的概念

### 5.2 v1 明确不做（Non-goals）

| 不做的功能 | 理由 |
| --- | --- |
| 课堂实时划词解释 | 技术形态完全不同（前端渲染问题而非 AI 问题），与 P1、P2 无关 |
| Past paper / 刷题讲解 | 先把讲解做透，避免功能分散 |
| 笔记生成、脑图、总结 | 功能堆砌，与定位无关 |
| 多人协作 / 分享 | 无核心价值关联 |
| 移动端原生 App | Web 优先，降低开发成本 |

## 6. 能力边界定义

### 6.1 能做

- 基于文本课件的概念讲解、类比、举例
- 按结构化参数调整表达方式
- 判断内容是否符合给定风格约束

### 6.2 明确做不到 / 效果不可靠

| 边界 | 产品应对 |
| --- | --- |
| 扫描件、手写笔记等图片型课件 | 上传时检测并提示不支持（v1） |
| 课件之外的知识 | 溯源约束 + 明确标注"以下内容超出课件范围" |
| 判断考试重点 | 不提供此功能，避免误导 |

原则：所有超出课件范围的内容必须显式标注。

## 7. 技术方案约束

### 7.1 架构

```
课件上传
   ├─→ 切片 & 向量索引
   └─→ 术语表提取（每门课一次性，模型辅助 + 用户可增删）
                ↓
用户提问 → 检索 agent（取 Top-K 相关片段）
                ↓
            讲解 agent（生成）
                ↓
            风格审查 agent
              ├─ A 类：规则计算（含术语表字符串匹配，零模型成本）
              └─ B 类：低成本模型判断
                ↓
          ──不合格──→ 重生成（上限 2 次）
                ↓ 合格
            输出 + 反馈收集 → 更新风格配置
```

术语表的三处复用：审查侧的分母来源 / 检索信号 / F4「没看懂」概念的锚点。一份数据三处用，避免为单一指标引入额外链路。

### 7.2 多智能体的必要性论证

本项目使用多 agent 不是为了技术展示，而是因为：

生成方与审查方的目标相反。 讲解 agent 的目标是把内容讲清楚，它没有动机去检查自己是否啰嗦；风格审查 agent 的唯一目标是执行约束。让同一个 agent 兼任两职，会出现自我合理化。

这与"防幻觉需要独立核查"是同一类设计原理。

### 7.3 模型选型约束

- 不硬编码模型，做抽象层，配置可切换
- 选型依据为实验结果而非主观印象：候选模型在固定风格约束下的指令遵循稳定性，通过 §8.2 的漂移实验测定
- 分层调用：
  - 讲解 agent → 中高端模型（质量敏感）
  - 风格审查 agent → 低成本模型；可规则化的维度直接用程序计算，不调模型
- 课件内容会话内不变 → 必须启用 prompt caching

### 7.4 上下文策略

- 单轮上下文 = 系统提示 + 风格配置 + 检索片段 + 最近 N 轮对话摘要
- 不累积全部历史，超过阈值后对早期对话做摘要压缩
- 目的：同时控制单次长对话内的幻觉与成本膨胀

## 8. 评测方案

### 8.1 风格维度的量化定义

风格维度分为常驻与条件激活两类，激活与否由用户的风格配置决定。未激活的维度不计入遵循度分母，否则单语用户的得分会被虚高拉起。

**A 类 · 规则可计算（零模型成本）**

| 维度 | 激活条件 | 计算方式 | 达标线 |
| --- | --- | --- | --- |
| 详细程度 | 常驻 | 平均段落字数、总输出长度 | 按配置区间 |
| 冗余句式 | 用户已标记 ≥1 条 | 被标记句式是否复现 | 0 次 |
| 引用长度（合规约束） | 常驻 | 单段原文引用字数 | ≤ 100 字，见 §12.1 |
| 讲解语言一致性 | 讲解语言 ≠ 课件语言 | 目标语言字符占比 | 按配置，±5% |
| 术语处理 | 同上 | 命中术语表的词中，符合所配策略的比例 | ≥ 90% |

术语处理为三值配置参数，非布尔项：

| 取值 | 含义 |
| --- | --- |
| keep_original | 保留原文术语，不翻译 |
| translate_with_source | 译文 + 原文括注 |
| translate_only | 仅用译文 |

单语场景（讲解语言 = 课件语言）下该参数为 N/A，整项不激活。

术语识别方案：不在生成文本中现场识别，而在课件上传阶段一次性提取该课程术语表（加粗/标题/定义框词汇、跨页高频名词短语、Glossary 页），审查时退化为字符串匹配。

误差方向说明：术语表必然存在遗漏。遗漏项不计入分母，只会降低指标灵敏度，不会造成误判——误差方向是安全的。反之误收普通词会导致误判，故提取策略取保守，宁漏勿错，并提供用户手动增删入口。

**B 类 · 需模型判断（用低成本模型）**

| 维度 | 激活条件 | 判断方式 |
| --- | --- | --- |
| 是否使用类比/举例 | 用户已配置偏好 | 二分类 |
| 结构（先结论 vs 先铺垫） | 常驻 | 二分类 |
| 讲解深度（只讲是什么 vs 讲原理） | 常驻 | 三档评分 |

**设计要点**

- A 类优先，能用规则解决的绝不调模型。这是成本控制的关键，也是可讲的设计决策。
- 遵循度按维度分别报告，不做单一混合分。混合分会掩盖结构性问题——例如"长度控制良好但从不给类比"仍可能得到 88% 的表面达标分。§3.2 的 ≥85% 应理解为各激活维度均需达标，而非平均值达标。
- §8.2 的漂移实验不受激活机制影响：该实验固定单一配置，激活维度集合恒定，前后可比。

### 8.2 关键实验：漂移衰减曲线

**实验设计**

- 固定一份风格配置 + 一份课件
- 条件组：有审查 agent / 无审查 agent
- 各跑 20 轮对话，每轮计算风格遵循度
- 绘制遵循度 vs 轮次曲线

**预期产出**：证明审查 agent 的必要性，并量化其收益。

同一框架用于模型选型：在多个候选模型上重复实验，选择衰减最平缓者。

这张图是本项目在面试中最有力的材料——它同时证明了指标定义能力、对照实验设计能力、以及用数据支撑设计决策的能力。

### 8.3 评测集构造

| 项目 | 方案 |
| --- | --- |
| 来源 | 公开课程材料（如 MIT OCW）为主；同学课件需走知情同意流程，详见 §12.1 ⚠️ |
| 规模 | 50–100 条问答对 |
| 标注 | 风格维度由脚本自动计算；溯源正确性人工标注 |
| 一致性 | 溯源标注由 2 人独立完成，计算一致率，不一致处讨论对齐 |

### 8.4 上线达标线

v1 可上线的条件：

- 20 轮后风格遵循度 ≥ 85%
- 溯源率 ≥ 90%
- 单会话成本 < $0.05
- 无严重 bad case（见 §10）

## 9. 成本与延迟预算

### 9.1 成本

| 项 | 预估 | 说明 |
| --- | --- | --- |
| 单轮讲解 | 待实测 | 开启 caching 后主要成本在输出 |
| 单轮审查 | 应 < 讲解成本的 15% | 低成本模型 + 规则前置 |
| 重生成 | 触发率目标 < 20% | 触发率过高说明讲解 agent 的提示词需优化 |
| 单会话（20 轮） | 目标 < $0.05 | — |

要求：从第一天起将每次调用的 token 数与成本写入日志。 面试必问单位经济，能报出具体数字与结构的候选人极少。

### 9.2 延迟

| 环节 | P95 要求 |
| --- | --- |
| 首字返回 | < 3s |
| 完整讲解 | < 15s |
| 审查不通过导致的重生成 | 用户不应感知到明显额外等待 → 采用流式输出 + 后置审查提示，或先审查再流式输出（需权衡，见下） |

待决策：审查 agent 会引入额外延迟。两种方案：

- A · 先审后出：质量有保证，但延迟翻倍
- B · 边出边审：延迟低，但可能出现"输出到一半被判定不合格"的尴尬

倾向 A，但需实测延迟能否接受。若不可接受，考虑仅对 A 类规则维度做实时检查（速度快），B 类维度异步检查并用于更新配置。

## 10. Bad Case 与兜底设计

| 场景 | 表现 | 兜底方案 | 用户可见文案（示例） |
| --- | --- | --- | --- |
| 课件为扫描件/图片 | 无法提取文本 | 上传时检测并拒绝 | 「这份课件是图片格式，暂时读不了。可以试试文字版的 PDF。」 |
| 提问超出课件范围 | 模型可能编造 | 检索无相关片段时显式声明 | 「这个内容课件里没有提到，我可以基于通用知识讲，但请以课程材料为准。」 |
| 风格审查连续 2 次不通过 | 无法生成合规输出 | 降级输出 + 说明 | 「这次讲解可能不太符合你设定的风格，你可以点反馈告诉我哪里不对。」 |
| 模型 API 不可用 | 请求失败 | 切换备用模型 / 明确报错 | 「服务暂时不可用，稍后再试。你的课件和设置都还在。」 |
| 超时 | 长时间无响应 | 30s 超时中断 | 「这次响应超时了，要重试吗？」 |
| 用户上传非课件文件 | 讲解无意义 | 内容类型检测 | 「这份文件看起来不像课件，确认要继续吗？」 |
| 用户上传含个人信息的文件 | 隐私风险 | 提示用户 | 见 §12 |

原则：兜底文案必须具体，不写"请稍后重试"这类无信息量的提示。

## 11. 假设清单

0→1 项目与成熟产品的关键差异：大量需求尚未被验证。必须显式区分「已验证」与「仍是猜测」，否则会把猜测当事实做进产品。

| 编号 | 假设 | 状态 | 验证方式 |
| --- | --- | --- | --- |
| A1 | 风格漂移是普遍现象且令用户烦躁 | **已验证** | 同学群体中普遍存在，有明确替代行为 |
| A2 | 大部分用户无法用语言描述自己想要的风格 | 部分验证 | 同学群体中普遍存在 |
| A3 | 用户愿意为解决此问题付费 | **未验证** | 目前仅有 1 个自述数据点（项目发起人本人）。自述意愿是弱证据 |
| A4 | 平时（非考试季）有足够使用动机 | **已验证** | 每个教学周都有至少3-4个不同课程的课件需要学习。 |
| A5 | 「样例选择」比「文字描述」更有效 | 未验证 | A/B 对比：两种配置方式下的风格满意度 |
| A6 | 目标用户规模足够 | 未验证 | 需竞品调研 + 小红书等渠道试水 |

## 12. 合规与伦理

前置声明：以下为产品视角的风险梳理，非法律意见。撰写者不是律师。正式对外开放前将由专业人士复核。对当前的封闭内测形态，本清单作为设计约束使用。

适用法域：目标用户主要在新加坡，但未来可能面向境内，故两套框架并列考虑。部署地与用户所在地共同决定适用规则。

### 12.1 著作权（核心风险）

问题：大学课件的著作权通常归授课教师或学校，学生并非权利人。本产品涉及四个动作：存储、切片、API 传输、生成输出。前三者涉及复制，输出还可能涉及改编与信息网络传播。

**已纳入设计的约束**

| 措施 | 作用 |
| --- | --- |
| 课件仅存于用户个人空间，不跨用户共享、不建公共库、不做跨用户检索 | 将使用场景限定在个人学习 |
| 不用于模型训练 | 避免内容以任何形式沉淀进模型 |
| 一键删除；注销即清空 | 用户可随时终止 |

表述注意：上述措施的作用是显著降低风险，而非使行为自动落入"合理使用 / fair dealing"的安全区。中国著作权法的合理使用与新加坡 Copyright Act 2021 的 fair dealing 框架不完全等同，且判断需综合使用目的、商业性、对原作品市场的影响等因素。PRD 与对外文档中不宣称"属于合理使用"。

**需补充的措施**

1. 上传确认文案
   「我确认这是我本人所修课程的材料，仅用于个人学习，且未被标注为保密或禁止外传。」
2. 输出侧引用限制
   - 溯源引用单段上限 100 字
   - 系统提示词中明确禁止大段复述原文
   - 产品必须是"讲解"，一旦滑向"课件重述"即越界
   - 该限制应写入风格审查 agent 的检查维度（见 §8.1）
3. 异议处理流程（半页纸即可）
   ```
   接收异议（公开邮箱）→ 定位相关内容 → 删除并回复 → 记录留档
   ```
4. 对外宣传禁止事项
   绝不出现「覆盖 XX 大学 XX 课程资料」类表述。这是最直接的不利证据，且与产品定位（个人学习工具，非资料库）相矛盾。

### 12.2 个人信息保护

适用：新加坡 PDPA；若面向境内用户，另适用《个人信息保护法》。

**风险点**：
- 课件本身可能含教师姓名工号、学生名单、成绩表
- 产品收集学习记录、风格配置、提问内容

**措施**：

| 措施 | 说明 |
| --- | --- |
| 隐私政策明示 | 收集什么、用途、存储在哪个国家、传给哪些第三方 API |
| 跨境传输披露 | 调用境外模型 API 即构成数据出境，必须明示 |
| 敏感信息检测 | 上传时扫描常见模式（证件号、学号成绩表），命中则提示用户并删去敏感信息。 |
| 导出与删除 | 两套法律的共同要求 |
| 未成年人 | 少数情况存在。不做个性化推荐，不收集非必要信息 |

### 12.3 第三方 API 的数据条款

核心问题：产品向用户承诺「不用于训练」，但上游服务商是否承诺尚待查证。

若上游条款与产品隐私政策冲突，则产品承诺构成虚假陈述。

**接入前必须查证的三项：**

1. 该服务商的开发者条款是否明确不将 API 输入用于训练（企业版通常承诺）
2. 数据保留期限
3. 数据存储地

结论需写入 §13.3 数据流向图，并与隐私政策逐条对齐。

### 12.4 备案与资质

| 法域 | 现状判断 |
| --- | --- |

### 12.5 内容安全与免责

- 接入基础内容过滤（多数 API 自带，需确认已开启）

## 13. 埋点与数据回流

### 13.1 必要埋点

| 事件 | 关键字段 | 用途 |
| --- | --- | --- |
| 课件上传 | 文件类型、页数、处理耗时、成功/失败 | 支持率优化 |
| 风格样例选择 | 选中项、选择耗时 | 验证 A5 |
| 每轮讲解 | token 数、成本、延迟、风格遵循度得分、是否触发重生成 | 核心质量与成本监控 |
| 反馈点击 | 反馈类型、当前配置 | 配置更新 + 问题归因 |
| 会话结束 | 总轮次、总时长 | 北极星指标 |
| 新开会话 | 是否因不满意而新开 | 直接验证 P2 是否被解决 |

### 13.2 数据回流

用户反馈（"太啰嗦""例子没懂"）→ 更新个人风格配置 → 同时汇总为风格维度的整体分布，用于优化默认样例的设计。

这是产品的飞轮：用的人越多，初始样例越贴近真实需求分布，新用户找到合适风格的速度越快。

### 13.3 数据流向图

需明确绘制并与隐私政策逐条对齐（要求见 §12.3）：

```
用户上传课件
   → 应用服务器（存储地：待定，需在隐私政策中披露）
   → 切片 & 向量化（是否调用第三方 embedding 服务？若是，构成第二次数据出境）
   → 检索片段 + 提问 → 模型 API（服务商、存储地、保留期限、是否用于训练：待查证）
   → 输出返回用户
   → 风格遵循度指标 & token 用量写入日志（不含课件原文）
```

**待确认项（接入前必须逐条查清并填入）：**

| 项 | 状态 |
| --- | --- |
| 模型 API 服务商的训练用途条款 | 待查证 |
| 数据保留期限 | 待查证 |
| 数据存储地 | 待查证 |
| embedding 服务是否为第三方 | 待决策 |
| 应用服务器部署地 | 新加坡 |
