### 🔧 React #418 的修复（2026-09-10）

**你的推断是对的，已坐实。** `useState(() => makeFlips(TOTAL_STEPS))` 写在**客户端组件**里，
而客户端组件的渲染在 **SSR 时跑一次、hydrate 时又跑一次**，惰性初始化两侧各执行一遍，
两次 `Math.random()` 约有一半概率不同——不同才报，相同则静默通过，正是「报与不报各半」。

**修法**：随机上移到服务端页面抽一次，作为 prop 传给客户端组件。
prop 随 RSC 载荷序列化，两侧渲染同一份数据；页面是 `force-dynamic`，每次加载仍是新的一次抽取。
客户端再把它冻进 state（`commit()` 后的 `router.refresh()` 不会重排左右）。

**新护栏（覆盖你点出的缺口）**：判据从「函数对不对」上移到**「随机发生在哪一侧」**——

- 从 `lib/style/` **推导**出「函数体里有 `Math.random` 的导出函数」名单（不写死），
  再要求**任何 `"use client"` 组件都不得引用**其中任何一个；
- 允许控制：服务端页面**必须**仍在调 `makeFlips` 并以 prop 传下去
  （少了它，把随机整个删掉也会让上一条全绿，而那是最坏的结果——位置恒定）；
- 反向控制：把修复前的写法塞回源码，判据**必须**报出问题。

⚠️ **这条护栏的第一版是空转的，被它自己的反向控制抓了出来**：初版只查字面的
`Math.random(`，而真实 bug 是 `makeFlips(...)`——随机藏在一层调用后面，客户端源码里
根本没有那几个字。第二版按函数体推导名单后才真的会红。**判据自己也要先过反向控制**（F16）。

（同时修掉推导里的两处误判：注释写在下一个 `export` 之前会落进上一块，导致
`configFromPicks` 被算成随机源；`rng = Math.random` 这种把随机函数当值传的写法后面跟的是
`)` 不是 `(`，导致 `makeFlips` 反而被漏判。现在先剥注释、按标识符引用匹配。）

**四条读这张表时要知道的：**

1. **`user_id` / `event_type` / `arm` / `session_id` / `schema_version` / `created_at` 是列，不在 payload 里。**
   有一条断言禁止在 payload 里重复存它们——两处存同一个值就有两处会漂。
2. **「缺」判三种**：键不存在 · 值是 JSON `null`（前端拿到 `undefined` 序列化的形态）·
   值是空字符串（变量名拼错的形态）。三者在 jsonb 里长得都不一样，对分析同样无用，一律 `23514`。
3. **必需 ≠ 全部。** `style_text_mapped` 失败时还会多一个 `failure`
   （`max_tokens` / `refusal` / `no_text_block` / `rate_limited` / `bad_credentials` /
   `connection` / `api_error` / `not_json` / `value_out_of_domain`，**是分类不是文案**——
   记人话的话事后要按正则分组，而正则会随文案漂）。
4. **事件类型的取值域也由这张表给**：未知 `event_type` → 函数返回 `NULL` → payload 判假。
   不另立第二条 CHECK（同一份清单两处出处必然漂，F13）。

### 判红的理由（这一条比现象重要）

**不是「网络会抖」——网络抖是必然的。** 红的是**失败之后没有任何补偿**：
事件丢了、日志里一行、然后就没了。而 shown/chosen 配对是算位置效应的基础，
缺 shown 的那一步位置效应无从算起——**那正是阶段 3 做位置随机化要保住的东西**（F37）。

### 为什么固定在 step 1（**推断，与证据相符，未坐实**）

step 1 的事件是这次页面加载中**浏览器对 Supabase 主机的第一个请求**
（服务端组件那次取数发生在服务端）。浏览器此时可能去复用上一次导航留下的
keep-alive 连接，而服务端早已按空闲超时关掉了它——复用失败即 `ERR_CONNECTION_CLOSED`。
浏览器**会**自动重发幂等的 GET，**但不会自动重发 POST**，所以页面本身照常加载，
只有我们这条 POST 死掉；step 2–6 用的是已经握好手的连接。这解释了「固定在 step 1」
与「概率性」两点。

**能确证的只有三件事**：① `createBrowserClient` 在浏览器里是单例
（`@supabase/ssr` 源码，`cachedBrowserClient`），所以「每次发事件新建 client」**不是**原因，
这条候选已排除；② 失败发生在 fetch 层，没有数据库错误码（`code: ""`）；
③ 浏览器不自动重发 POST。真要坐实机制得抓一次 net-export，代价不值。

**而这不影响处置**：重试对上面任何一种机制都有效。

### 处置：重试 + 有序排队 + 持久化（口径 **F42**）

**三个候选里为什么不选「把首屏事件延后到 client 就绪」**：它只降低概率、
让这个 bug 更罕见因而**更难被抓到**——那是拿判据的分辨力去换一个好看的数字
（同 F16 反对的那件事）。而且它对 step 2–6 上同样会发生的网络抖动毫无作用。

`web/lib/style/events.ts` 的 `createEventQueue`：

| | |
| --- | --- |
| **瞬时失败** | 网络层拒绝（`code` 为空）/ `PGRST301` / 5xx → 退避重试 `300/1000/3000/8000ms`；**用尽后留在队列里**等下一次 `enqueue` 或下一次页面加载，**不丢** |
| **永久失败** | `23514` / `42501` 这类内容或权限问题 → **不重试**、丢弃、并**吵**（`dropped` 计数 + 页面上一句话 + `console.error`）。那是「我们构造了一条坏事件」，要的就是吵 |
| **分类方向** | 瞬时是**白名单**，其余一律永久。把瞬时当成永久 → 一条响亮的报告；反过来 → 静默空转 |
| **有序** | 永远发 `queue[0]`，成功或永久失败才出队。乱序会让 `chosen` 先于同一步的 `shown` 落库——配对还在，但「先看到再点选」这个事实没了 |
| **持久化** | 落 `sessionStorage`。`router.refresh()` 不卸载组件，但用户点「回到首页」会。三个风格页挂载时各冲一次队列 |
| **服务端** | route handler 没有队列可排（请求结束进程就走），所以在这次请求里把重试做完，阶梯更短（`200/700ms`）——用户正在等这一屏 |

⚠️ **残留风险如实登记**：关掉标签页且**再也不回任何风格页**的那部分仍然会丢。
这一条**靠检出兜底，不靠承诺**——见下面的判据与人工清单 1.2b。
`sendBeacon` / `keepalive` 兜底已记进 `f1_samples/README.md` §二，带触发条件。

### 二、Docker 镜像：**第一次构建成功，并当场抓出一个只有真构建才会出现的 bug**

```
docker build -f api/Dockerfile -t f1-api .     ✅ 887MB
docker run（缺环境变量）                        ✅ 启动即失败并点名变量
docker run（配全）→ /health 200 · /me/style 401  ✅
```

**抓出的 bug**：`from slicer import slice_document` 报
`ImportError: cannot import name 'slice_document' from 'slicer' (unknown location)`。

机制：uvicorn 把 cwd（`/srv`）放进 `sys.path` **第一位**，而 `COPY slicer /srv/slicer`
放的是**项目目录**（真包在 `/srv/slicer/slicer`），它没有 `__init__.py`
→ PathFinder 把它当**命名空间包**直接返回；setuptools 的 editable finder 是
`sys.meta_path.append` 进去的，**排在 PathFinder 之后**，根本轮不到。
`unknown location` 就是命名空间包的签名。

**本机跑不出来**（cwd 是 `api/`，那一位上没有同名目录）——
这正是「先本地构建一次再交付」买到的东西。修法：pip 装的那两个包落到 `/opt/pkgs/`，
离开 `sys.path`。`explain` / `retrieval` / `a_rules` 不受影响（它们走路径注入，
`insert(0, ...)` 插在 cwd 前面）。

### 五、阶段 6（部分）· §13.0 四个讲解事件 + 补上 `course_id`/`deck_id`

#### `course_id` / `deck_id`：阶段 4 登记的触发条件成立了

阶段 4 建表时写的是「**触发条件**：事件开始涉及具体课件时（F2）」。
`explain_turn` / `retrieval_executed` 就发生在一门具体的课上，触发。

**两列刻意不加外键**，三条路各有各的坏处：

| | 后果 |
| --- | --- |
| `on delete cascade` | 删一门课，那门课的**历史事件跟着没了**——删课是一次整理，不该悄悄改掉上个月的北极星指标 |
| `on delete set null` | 更糟：行还在，**再也不知道属于哪门课**。表现是历史分组数据慢慢变少，没有任何东西会红 |
| **不加**（现行） | uuid 原样留着，删课之后仍然分得开组 |

所以「不加外键」是承重的，不是漏了。

⚠️ **一处刻意接受的不一致，如实登记**：`course_id` 现在就被真的写进去了

天然只涉及一份讲义。按阶段 4 自己的理由（「恒 null 的列会让读的人以为可以按它
分组，然后得到一张全是空值的表」），`deck_id` 本该等到上传页再建。
两列一起建的理由是 PRD §13.0 把它们列在一起、一次 alter 比两次少一条迁移；
**代价是那个错觉提前存在了一轮**。挡它的是迁移里那条 comment（`\d+` 看得到）
与这一段。**第一个真正填它的事件在上传侧**（`deck_upload_failed` / `deck_uploaded`），

判据是**数据在哪**，不是「前端/后端」。这四个的全部字段都产生在

#### 一条本轮新发现的相互作用（口径 **F50**）

`f1_event_payload_ok` 把 **JSON null 判成「没有」**（那是防前端 `undefined` 的，对）。
于是 null 有含义的字段**不能**进必需清单：

- `all_activated_passed` —— 无维度可判时为 `null` **不是 `true`**（口径 D42）
- `first_token_latency_ms` —— 不流式测不了，**不塞假数**（PRD §9.2）

⚠️ **代价如实登记**：这几个字段因此**没有护栏**，真漏了不会红。
补法不是塞进现在这个清单（那会把「有意义的 null」和「漏了」再压成同一件事），
而是另立 `payload ? 'k'` 那种判据。**触发条件**：内测第 1 周数据落盘后若发现缺失。

⚠️ **在 parse 之后查，不在之前。** 之前查要我们自己算一次 sha，
而 `content_sha256` 的出处是 `parse_pdf`——自己再算一份就是第二处出处（F13），
它漂开的表现是「重复检测永远查不到」，没有任何东西会红。
代价是白解析一次（本地 CPU，**不花钱**：嵌入在这之后）。
测试里有一条把三个来源（`parse_pdf` / `hashlib` / 我们查的那个）钉在一起。

### `deck_upload_failed`：八类，**不压成「上传失败」**

PRD §13.0 把它登记为「本批不做」，触发条件「接前端与账号之后」，
理由是「失败分类**依赖前端的上传流程形态**」。上传页做出来了，触发。

「失败分类」这四个字是硬要求：**用户侧的处置每一类都不同**。

| 分类 | 压成「上传失败」的后果 |
| --- | --- |
| `pptx_not_implemented` | 他会以为**永远**不支持，去手动转 PDF —— 而我们下一次交付就会支持 |
| `duplicate_in_course` | 他会再传一次，再失败一次。而事实是**什么都不用做**，它已经在这门课里了 |
| `unparsable` | 他会重试一个**永远不会成功**的上传 |
| `db_error` / `unknown` | 混进上面几类之后，「重试有没有用」这个问题答不出来 |

分析侧的代价是另一个：§3.2 的「课件支持率」分母里，`pptx_not_implemented`
（我们没做，**会随交付消失**）与 `unparsable`（这份文件读不了，**不会消失**）
不是同一件事。合成一个数之后，支持率的变化说不清是哪一边动了。

**`retryable` 取小**：把可重试判成不可重试，用户少点一次按钮；
反过来他会一直重试一个永不成功的上传。

### 一条新护栏：**闭集**（`f1_event_payload_ok` 管不了的那一半）

`f1_event_payload_ok` 只回答「这个键在不在」。它挡不住**值写错**：
一个拼错的 `unparseable`（多一个 e）**键在、非空、类型对，照样入库**，
然后在分析时变成一个新类别——而它看起来完全正常，只是某一类的计数莫名其妙少了。

新增 `f3_event_enums_ok()` + 一条**独立的** CHECK。为什么不塞进原来那条：
一条 CHECK 同时管两件事，失败时 23514 说不出是哪一件，而两件的处置不同
（补字段 vs 改拼写）。反向控制 **R15** 去掉它 → 拼错的值真的写得进去。

那个闭集**住在三处**（SQL 唯一出处 / Python 分类 / TS 文案），
所以有两条从**源文件解析回来**的比对（SQL → TS、Python → TS，口径 F33）。

### 🔴 两个本批抓出的缺陷

#### ① 同名同义的两个异常类

`api/api/ingest.py` 与 `api/api/supabase.py` **各有一个 `DuplicateDocument`**，
而 `main.py` 同时 import 两个（其中一个带着 `# noqa: F401 —— 保持符号可见`，
说明当时就觉得别扭）。

代价当场兑现：「先查后提示」在 `ingest.py` 里抛的是**它自己那个**，
而路由 `except` 的是**另一个** —— 两者无继承关系，于是那条重复提示掉进
兜底的 `except Exception`，被报成 **422「无法处理该 PDF」**。

> **同名同义的两个类，比两个不同名的更危险**：读代码的人看到
> `DuplicateDocument` 不会去确认它是哪一个，而 `except` 只认对象的真实类型。

已合并成一个（唯一定义处 `supabase.py`），并配两条断言：
两条 import 路径指向同一个对象、**源码里 `class DuplicateDocument` 只出现一次**
（后者防的是「又定义了一个恰好也叫这个名字的子类」，那时前一条仍可能绿）。

#### ② `verify:logic` 那条镜像比对**一直在跟一份不生效的定义比**

`parseSqlRequiredKeys` 用 `.exec()` 取**第一个**
`create or replace function f1_event_required_keys`，而那个函数被 replace 过三次
（5 个类型 → 9 个 → 11 个），**迁移按序执行，生效的是最后那一份**。

它一直是绿的，而且会一直绿——**绿的理由是它在跟阶段 4 那份已经不生效的定义比**。
连那条「解析出 5 个 event_type」的分辨力断言，也是靠读到旧定义才通过的。

这是 F16 的又一个形态：判据在它要区分的两种情况下取值相同
（旧定义与新定义里那五个 `style_*` 恰好一样），所以它**分不出「TS 与生效定义漂了」**。

改成取最后一个定义，并加两条：生效定义**必须**解析出 11 个类型；
**反向控制**——只取第一个定义时必须得到 5（上一条的分辨力靠它）。
比对本身改成子集比对（TS 只镜像五个 `style_*`，口径 F51），
且**不比「SQL 有而 TS 没有的」**——那是常态，比了会永远红然后被放宽成永远绿。

#### ③ 我自己写的两条断言在空转（同一个错犯了两次）

`verify_rls_local.mjs` 里的 `mkDoc` **返回的是错误对象（成功时 `null`），不是 id**。
我在两个地方把它当 `document_id` 用：

- 阶段 6 那节的「事件与它的 `course_id`/`deck_id` 都还在」→ `deck_id === did`
  是 **`null === null`**，那一半空转；
- 本批那节的「`deck_uploaded` 带 `deck_id` 写得进去」→ 插进去的是 null，
  **整条空转变绿**。

抓出它的是我在同一节里写的第三条断言（「这一列真的有非 null 的行」）。
两处都修了，并加了**夹具自检**：先断 `document_id` 确实是个 uuid，
再断**存进去的值等于它**（而不是「插入没报错」）。

> 教训：**夹具的返回值也要先被断一次。** 否则断言测的不是它声称的东西。

| --- | --- | --- |
| **重生成不进轮次** | 按 `regenerations` 累加 | 一个字段两种含义，成本表与北极星指标永远对不上，**而两边看起来都是对的** |
| **失败不进轮次** | 「发一次请求就 +1」——最自然的写法 | 一次 503 / 404 / CORS 被挡，**用户一个字都没看到**。按请求计数会把失败算进「平均会话轮次」的分子，那个数只会**偏高**，看起来像产品更粘 |

口径住在 `web/lib/explain/turns.ts` 一处，**纯函数**，18 条断言钉着它。
其中两条值得单记：

- `nextTurnIndex` 与 `answeredCount` **是两个函数而不是一个**（差 1，语义不同）。
  合成一个会让调用方在某处忘记 ±1，而那种错在数据里是**整体偏移一格**。
- 一条断言读 `nextTurnIndex` / `answeredCount` 的**函数源码**，要求里面
  不出现 `regenerations` —— 前端现在天然做对了（重生成在服务端一次请求里面，
  前端看不见），但**没有这条断言，哪天有人按它累加也不会红**。

### `session_id` 的占位口径 + **一个方向明确的偏差**

**一次页面加载 = 一个 session**（PRD §3.4.5 的切分规则至今未定），
服务端抽、当 prop 传（React #418：客户端组件 SSR 与 hydrate 两侧取随机数会分叉，
而**它是「平均会话轮次」的分组键**，分叉会让同一次会话的轮次落到两个 session 上）。

⚠️ **如实登记那个偏差**：用户刷新页面 → 新 session，轮次从 1 重新开始。
一个问了 10 轮、中间刷新 3 次的用户会被记成 4 个会话 ——
**「平均会话轮次」被系统性压低**。

偏差方向是**单向**的（只低估，不高估），这一点让它比方向不明的偏差好处理：
内测第 1 周的数据可以当**下界**读，而不是当估计值。
**触发条件**：那个数要用来做决定（而不只是看趋势）时，切分规则必须先定下来。

### 等待态是这一页最要紧的交互

一次请求 **30–60 秒**（生成 + 最多 2 次重生成），而且**不流式**
（`explain/prompt.py`：`first_token_latency_ms` 恒 null，「不塞假数」）。

| 做法 | 理由 |
| --- | --- |
| **只允许一轮在飞** | 不流式意味着第二次提交不会「插队」，只会让两个几十秒的请求同时跑，而**先回来的先渲染** —— 轮次顺序会与提问顺序相反，而 `turn_index` 是按「用户看到第几次回答」计的 |
| **一个走着的计时器** | 没有它，**一个 40 秒的等待与一个卡死的请求在页面上长得一模一样**。它不是阈值判断，只是让等待可见（同 F38 对 `dwell_ms` 的处置：只采集不判读） |
| **明说别关页面** | 不流式，没有中间结果可续 |
| 失败那一轮说清**它不计入轮次** | 否则用户以为自己「用掉」了一轮 |
